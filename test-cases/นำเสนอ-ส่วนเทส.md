# นำเสนอส่วนเทส — Middle (ระบบตรวจจับการล้ม)

ตัวเลข ณ 23 พ.ย. 2026 · โค้ด commit `49fc17a` · ใช้เวลาพูดราว 3 นาที + demo 2 นาที
ก่อนวันจริงเช็กตัวเลขกับชีต "สรุป" อีกครั้ง ถ้าเทสเพิ่มแล้วตัวเลขจะเปลี่ยน

## จำประโยคเดียว

> **ในส่วนที่ทดสอบในเครื่อง ระบบโทรแจ้งทำงานตรงเวลาแม้ AI ใช้ไม่ได้ และการทดสอบเจอปัญหา 15 ข้อก่อนถึงมือผู้ใช้ แต่ยังไม่ได้ทดสอบล้มจริงครบทั้งระบบ**

---

## สไลด์ 1 — Problem

**หัวข้อ:** ระบบนี้พลาดแล้วไม่มีใครรู้

- ล้มแล้วไม่แจ้ง = ไม่มีคนไปช่วย · แจ้งผิดบ่อย = คนเลิกเชื่อ
- มีหลายส่วนต่อกัน: ESP32 → โมเดล → Express → ฐานข้อมูล → แอป → โทร
- Figma เอกสาร และโค้ดไม่ตรงกันหลายจุด จึงตอบไม่ได้ว่าแบบไหนถูก
- ทดสอบบนฐานข้อมูลจริงไม่ได้ เพราะอาจทำให้ระบบจริงไม่โทร

**พูด:** "ระบบอื่นพังแล้วผู้ใช้บ่น แต่ระบบนี้พังแล้วผู้ใช้อาจบ่นไม่ได้ งานเทสจึงต้องตอบ 2 คำถาม คือ ตอนเกิดเหตุระบบทำงานไหม และเรารู้ได้อย่างไรว่ามันถูก"

## สไลด์ 2 — Solution

**หัวข้อ:** จาก requirement ถึงหลักฐาน

| ขั้น | ทำอะไร |
|---|---|
| 1. ตั้งเกณฑ์ | ใช้ TDG_BA, Role 0.2 และ User Story 16 เรื่อง แล้วเทียบโค้ด |
| 2. ออกแบบ | 427 เคส ใช้ ECP / BVA กับช่องกรอก และแบ่งความสำคัญตามความเสี่ยง |
| 3. แยกจากระบบจริง | Twilio จำลอง Express ไม่ต่อฐานจริง แอปเทสบน emulator แบบปิดเน็ต |
| 4. รันและเก็บหลักฐาน | สคริปต์รันทีละเคส บันทึก log และภาพหน้าจอ |
| 5. ยืนยันก่อนแจ้ง | ทำซ้ำหรือมีตัวเทียบ ก่อนสรุปว่าเป็นบั๊ก |
| 6. ติดตาม | Dev แก้ → เทสซ้ำ → ปิด ในชีตเดียว |

**พูด:** "เราไม่ได้เขียนเคสจากสิ่งที่แอปทำอยู่ แต่เขียนจาก requirement ถ้าแอปไม่ตรง ถือว่าเป็นบั๊กหรือคำถามถึงทีม ไม่แก้เคสให้ผ่าน"

## สไลด์ 3 — Result: ภาพรวม

| | เคส |
|---|---:|
| ออกแบบ | 427 |
| **ทดสอบแล้ว** | **104 (24%)** |
| Passed | 63 |
| Failed | 13 |
| Pending รอทีมยืนยัน หรือทำไม่ครบขั้น | 28 |
| ยังทดสอบไม่ได้ (Blocked) | 323 |

- ใน 76 เคสที่ตัดสินผลได้ ผ่าน 63 (83%)
- เคสความสำคัญสูงทดสอบแล้ว 51 จาก 199
- บั๊ก 15 ข้อ: High 2 · Medium 8 · Low 5 (Frontend 8 · Backend 5 · ML 2)
- คำถามถึงทีม 111 ข้อ มีคำตอบแล้ว 10

**พูด:** "ตัวเลขที่ต้องบอกตรงๆ คือ 24% ที่เหลือไม่ใช่ไม่ทำ แต่ 249 จาก 323 เคสติดเรื่องเดียว คือยังไม่มีฐานข้อมูลสำหรับทดสอบแยกจากของจริง"

## สไลด์ 4 — Result: สิ่งที่พิสูจน์แล้ว

| เรื่อง | ผลที่วัดได้ | เคส |
|---|---|---|
| ไม่มีคนกดรับ → โทร | โทรวินาทีที่ 60.1 ครบ 2 เบอร์ | ESC-001 |
| ส่งคำสั่งรับทราบเข้าหลังบ้านวินาทีที่ 55 → ยกเลิก (ยังไม่ได้กดปุ่มในแอป) | ไม่โทรจนถึงวินาทีที่ 90 | ESC-002 |
| AI ไม่มีคีย์ / ช้า / คีย์ผิด | ยังโทรวินาทีที่ 60.1–60.3 ด้วยข้อความมาตรฐาน | ESC-017, 018, 019 |
| ไม่มีคีย์ หรือใช้คีย์ของแอปส่งเหตุการณ์ปลอม | ถูกปฏิเสธ 401 | API-002, 003, 033 |
| ผู้ดูแลระบบ | ผิด 5 ครั้งแล้วล็อก, หมดอายุเมื่อไม่ใช้งาน | API-056, 081 |
| หลังบ้านไม่รั่ว | คีย์ 3 ตัวไม่โผล่ใน log, อ่านฐานโดยไม่ login ได้ 0 แถว | SEC-009, 001 |

(โทรในตารางนี้เป็น Twilio จำลอง)

**พูด:** "จุดสำคัญคือ AI เป็นแค่คนร่างข้อความ ถ้า AI ล่ม ระบบต้องโทรอยู่ดี เราทดสอบ 3 แบบ โทรตรงเวลาทุกแบบ"

## สไลด์ 5 — Result: สิ่งที่เจอ

| บั๊ก | ถ้าไม่เจอจะเกิดอะไร |
|---|---|
| **BUG-013 High** ชื่อบริเวณมี `&` หรือ `<` แล้วข้อความสายโทรเป็น XML ที่ผิด | เสี่ยงโทรแล้วไม่ได้ยินข้อความ ขณะที่ระบบบันทึกว่าโทรสำเร็จ |
| **BUG-014 High** กดรับทราบแล้ว ล้มซ้ำใน 5 นาที ไม่แจ้ง (รอทีมตัดสินใจ) | กดรับการแจ้งผิด แล้วล้มจริงทันที จะไม่มีใครรู้ |
| BUG-008 เบอร์มี +66 กลายเป็นเบอร์อื่น | เสี่ยงสมัครผิดเบอร์ |
| BUG-007 วางเบอร์ที่มีขีด เลขท้ายหาย | เข้าแอปไม่ได้ |

**พูด:** "BUG-013 โหมดจำลองบอกว่าผ่าน แต่พอดักข้อความที่จะส่งจริงมาตรวจ พบว่าผิดรูปแบบ ถ้าดูแค่ผ่านหรือไม่ผ่านจะไม่เจอ"

## สไลด์ 6 — ข้อจำกัดและขั้นต่อไป

- **ยังไม่ได้ทดสอบ:** ล้มจริงจนโทร (E2E), ESP32, หน้าหลัง login, โทรจริงผ่าน Twilio
- **ผล API:** ส่วนใหญ่ใช้ ML จำลอง ไม่ต่อ Supabase · การกดรับทราบยังไม่ได้ตรวจบัญชีและสมาชิกบ้าน
- **ผล ML:** ตรวจการทำงานของ service ไม่ใช่ความแม่น
- **ต่อไป:** 1) Supabase ทดสอบ 2) Dev แก้ BUG-013 และทีมตัดสินใจ BUG-014 3) เทสซ้ำ 4) ESP32 และ E2E

# คำถามที่อาจโดนถาม

| คำถาม | ตอบ |
|---|---|
| ทำไมเทสแค่ 24%? | 249 จาก 323 เคสที่เหลือต้องมีฐานทดสอบ ถ้าเทสบนฐานจริงอาจทำให้เหตุการณ์จริงไม่ถูกโทร จึงเลือกไม่เสี่ยง และบอกทีมแล้วว่าต้องใช้อะไร |
| ระบบใช้งานจริงได้หรือยัง? | ยังสรุปไม่ได้ ยังไม่ได้ทดสอบทั้งระบบกับ ESP32 และมี High 2 ข้อที่ยังไม่ปิด |
| ความแม่นของโมเดลเท่าไร? | เป็นตัวเลขของฝั่ง ML ฝั่งเทสยังไม่มีข้อมูล CSI ที่ไม่ได้ใช้เทรน จึงยังไม่ยืนยัน |
| Pending ต่างจาก Failed อย่างไร? | Failed = ไม่ตรง requirement ที่ชัด · Pending = requirement ยังไม่ชัด หรือทำไม่ครบขั้น |
| รู้ได้อย่างไรว่าเป็นบั๊กจริง? | ทำซ้ำหรือมีตัวเทียบ เช่น ชื่อ "ห้องน้ำ" ผ่าน แต่ชื่อที่มี & ไม่ผ่าน · เทสที่ตกเพราะสคริปต์หรือเมนู Expo ไม่นับ |
| Passed ทั้งหมดอิง requirement ไหม? | 6 เคสคู่มือไม่ชัด จึงอิงโค้ดและระบุไว้ (API-005, 011, 056, 071, ESC-014, MLS-003) |
| ใช้เครื่องมืออะไร? | Excel, สคริปต์ Python เรียก API, Android emulator + adb, Jest ของโปรเจค |
| เทสเองหรือใช้ AI? | ตอบตามจริง: ใช้ AI ช่วยออกแบบเคส เขียนสคริปต์ รัน และบันทึกผล ส่วนที่ทำเองให้พูดตามที่ทำจริง (เช่น กำหนดขอบเขต ยืนยัน requirement ตัดสินใจไม่แตะฐานจริง) |

# อย่าพูด

- "เทสครบแล้ว" หรือ "เทส 100%" → ชีต "สรุป" คอลัมน์ % เทสแล้วนับ Blocked ด้วย
- "ผ่าน 83%" โดยไม่บอกว่าจาก 76 เคส
- "โทรจริงแล้ว" หรือ "ความแม่นผ่านแล้ว"
- "Dev แก้แล้ว" → ตอนนี้ทั้ง 15 ข้อยังไม่แก้
