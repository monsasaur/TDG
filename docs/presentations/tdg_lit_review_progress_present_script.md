# Script นำเสนอแบบละเอียด: TDG / Middle Fall Detection

เวลาเป้าหมาย: พูดเนื้อหา 24 นาที + ถามตอบ 6 นาที  
โทนการพูด: พูดแบบอธิบายเหตุผลของการออกแบบ ไม่อ่านสไลด์ทุกคำ และแยกให้ชัดว่าอะไรคือผลที่ทำแล้ว อะไรคือข้อจำกัด และอะไรคือแผนต่อไป

## วิธีใช้สคริปต์นี้

- ส่วน “พูดตามนี้” คือข้อความหลักที่ใช้ซ้อมพูดได้เลย
- ส่วน “จุดที่ต้องเน้น” คือประเด็นที่ควรพูดให้ชัด ถ้าพูดไม่ครบให้เลือกประเด็นนี้ก่อน
- ส่วน “ถ้ากรรมการถาม” คือคำตอบสำรอง ไม่จำเป็นต้องพูดตอนนำเสนอหลัก
- ถ้าเวลาเกิน ให้ตัดรายละเอียดใน Slide 9, 10, 15 และ 20 ก่อน แต่ห้ามตัด Slide 3, 7, 12, 17, 22 และ 23 เพราะเป็นแกนเหตุผลของงาน

## Slide 1: Middle ระบบตรวจจับการล้มด้วย WiFi CSI

เวลา: 0:00 - 0:40

เป้าหมายของสไลด์: เปิดให้กรรมการเข้าใจทันทีว่าโปรเจคนี้แก้ปัญหาอะไร ใช้เทคโนโลยีอะไร และแตกต่างจากระบบทั่วไปอย่างไร

พูดตามนี้:

สวัสดีครับ วันนี้ผมจะนำเสนอโปรเจค Middle ซึ่งเป็นระบบตรวจจับการล้มสำหรับผู้สูงอายุ โดยใช้ WiFi CSI หรือ Channel State Information เป็นข้อมูลหลักในการตรวจจับการเคลื่อนไหว

โจทย์ของงานนี้เริ่มจากสถานการณ์ที่พบได้จริงในบ้าน คือผู้สูงอายุอาจล้มในช่วงที่ไม่มีคนเห็น เช่น อยู่คนเดียว อยู่ในห้องน้ำ หรืออยู่ในห้องนอน ถ้าผู้ดูแลรู้ช้า การช่วยเหลือก็จะช้าตามไปด้วย

แนวคิดหลักของระบบนี้คือ เราต้องการตรวจจับเหตุการณ์การล้มแบบ passive คือผู้สูงอายุไม่ต้องกดปุ่ม ไม่ต้องสวมอุปกรณ์ และระบบไม่ต้องใช้กล้อง เพราะกล้องมีประเด็นเรื่องความเป็นส่วนตัว โดยเฉพาะในพื้นที่ส่วนตัวภายในบ้าน

วันนี้ผมจะเล่าตั้งแต่ปัญหา วิธีเดิมที่มีอยู่ งานวิจัยที่เกี่ยวข้องกับ WiFi CSI เหตุผลที่เลือกแนวทางนี้ แล้วจึงเข้าสู่ระบบที่พัฒนาไปแล้ว สถาปัตยกรรมปัจจุบัน ข้อจำกัด และแผนงานต่อไปครับ

จุดที่ต้องเน้น:

- Middle คือระบบดูแลผู้สูงอายุ ไม่ใช่แค่โมเดล Machine Learning เดี่ยว ๆ
- จุดขายคือ passive, privacy-friendly และต่อเข้ากับ workflow การแจ้งเตือนผู้ดูแล

Transition:

ต่อไปผมจะสรุปก่อนว่าการนำเสนอวันนี้จะตอบคำถามอะไรบ้างครับ

## Slide 2: วันนี้จะตอบ 4 คำถามหลัก

เวลา: 0:40 - 1:10

เป้าหมายของสไลด์: วางโครงเรื่องให้กรรมการตามได้ง่าย และบอกล่วงหน้าว่าจะไม่ลง implementation ทุกบรรทัด แต่จะเชื่อม literature กับระบบที่ทำจริง

พูดตามนี้:

โครงเรื่องวันนี้ผมจะตอบ 4 คำถามหลักครับ

คำถามแรก ปัญหาที่เรากำลังแก้คืออะไร และทำไมการรู้เร็วหลังผู้สูงอายุล้มจึงสำคัญ

คำถามที่สอง ทำไมวิธีที่มีอยู่ เช่น กล้อง wearable หรือปุ่มฉุกเฉิน ยังมีข้อจำกัดในบริบทการใช้งานจริงภายในบ้าน

คำถามที่สาม ทำไม WiFi CSI ถึงเป็นทางเลือกที่น่าสนใจสำหรับ fall detection แบบไม่ใช้กล้องและไม่ต้องสวมใส่อุปกรณ์

และคำถามสุดท้าย ตอนนี้ระบบ Middle ทำถึงไหนแล้ว มีส่วนประกอบอะไรที่ทำงานได้แล้ว และยังมีข้อจำกัดอะไรที่ต้องทำต่อก่อนใช้งานจริง

ผมตั้งใจให้เนื้อหาหลักอยู่ประมาณ 24 นาที เพื่อเหลือช่วงถามตอบประมาณ 6 นาทีครับ

จุดที่ต้องเน้น:

- งานนี้มีทั้ง literature review และ progress ของระบบจริง
- ไม่ได้ claim ว่าระบบ production-ready แล้ว แต่เป็น end-to-end prototype ที่กำลังเข้าสู่ช่วง validation

Transition:

เริ่มจากขนาดของปัญหาและ pain point ก่อนครับ

## Slide 3: ปัญหาหลักคือการรู้ช้าเมื่อผู้สูงอายุล้ม

เวลา: 1:10 - 2:20

เป้าหมายของสไลด์: ทำให้กรรมการเห็นว่าปัญหามีน้ำหนัก ไม่ใช่แค่ use case สมมติ

พูดตามนี้:

ก่อนอื่น fall detection ไม่ใช่แค่การจับเหตุการณ์หนึ่งครั้งว่า “ล้ม” หรือ “ไม่ล้ม” แต่เป็นปัญหาเรื่องเวลาที่ใช้ในการช่วยเหลือหลังจากเกิดเหตุครับ

จากข้อมูลของ WHO การล้มเป็นหนึ่งในสาเหตุสำคัญของการเสียชีวิตจากอุบัติเหตุทั่วโลก โดยมีผู้เสียชีวิตจากการล้มประมาณ 684,000 คนต่อปี และมีเหตุการณ์ล้มที่รุนแรงพอให้ต้องเข้ารับการรักษาทางการแพทย์หลายสิบล้านครั้งต่อปี

ในฝั่งผู้สูงอายุ ข้อมูล CDC ระบุว่าผู้สูงอายุ 65 ปีขึ้นไปในสหรัฐอเมริกามากกว่า 1 ใน 4 ล้มในแต่ละปี และมีการเข้าห้องฉุกเฉินจากการล้มประมาณ 3 ล้านครั้งต่อปี ตัวเลขเหล่านี้สะท้อนว่าการล้มเป็นเหตุการณ์ที่เกิดได้บ่อยและมีผลกระทบจริง

แต่ pain point ที่เราโฟกัสไม่ใช่แค่ “มีการล้มเกิดขึ้น” ครับ ประเด็นคือ ถ้าผู้สูงอายุล้มแล้วไม่มีใครเห็น ผู้ดูแลอาจรู้ช้า และการช่วยเหลือก็ล่าช้าไปด้วย ยิ่งผู้สูงอายุอยู่คนเดียวหรืออยู่ในพื้นที่ส่วนตัว ความเสี่ยงนี้ยิ่งสูงขึ้น

ดังนั้นระบบที่ช่วยตรวจจับและแจ้งเตือนได้เร็วจะช่วยลดช่องว่างระหว่าง “เกิดเหตุ” กับ “ผู้ดูแลรับรู้และตัดสินใจช่วยเหลือ” ซึ่งเป็นจุดที่ระบบ Middle พยายามเข้าไปช่วยครับ

จุดที่ต้องเน้น:

- อย่าเน้นตัวเลขอย่างเดียว ให้โยงกลับมาที่ “รู้ช้า = ช่วยช้า”
- ระบบมีเป้าหมายช่วย workflow การดูแล ไม่ใช่แทนแพทย์หรือวินิจฉัยโรค

ถ้ากรรมการถาม:

- ถ้าถามว่าใช้ข้อมูลประเทศไทยไหม: ตอบได้ว่าในรายงานบทที่ 1 ใช้ข้อมูล NSO และกรมควบคุมโรคประกอบ ส่วนสไลด์นี้ใช้ WHO/CDC เพื่อวางภาพรวมระดับสากล

Transition:

เมื่อรู้ pain point แล้ว ขั้นต่อไปคือแปลง pain point นี้เป็น requirement ของระบบครับ

## Slide 4: ระบบที่เหมาะกับบ้านต้องไม่เพิ่มภาระให้ผู้สูงอายุ

เวลา: 2:20 - 3:30

เป้าหมายของสไลด์: เปลี่ยนปัญหาให้เป็นข้อกำหนดของระบบ และใช้เป็นเหตุผลคัดเลือกเทคโนโลยี

พูดตามนี้:

จาก pain point เรื่องการรู้ช้า เราแปลงเป็น requirement ของระบบได้ 5 ข้อครับ

ข้อแรกคือระบบต้องเป็น passive ให้มากที่สุด ผู้สูงอายุไม่ควรต้องจำว่าต้องกดปุ่ม ต้องใส่นาฬิกา หรือต้องชาร์จอุปกรณ์ตลอดเวลา เพราะถ้าการทำงานของระบบขึ้นอยู่กับพฤติกรรมของผู้สูงอายุ โอกาสพลาดในชีวิตจริงจะสูงขึ้น

ข้อที่สองคือ privacy-first พื้นที่ที่เกิดการล้มอาจเป็นห้องนอน ห้องน้ำ หรือพื้นที่ส่วนตัว ถ้าระบบใช้กล้อง แม้จะทำงานได้ดีทางเทคนิค แต่ผู้ใช้และครอบครัวอาจไม่ยอมรับ

ข้อที่สามคือ real-time หรืออย่างน้อย near real-time เพราะถ้าระบบแจ้งเตือนช้าเกินไป ก็ไม่ตอบโจทย์ emergency workflow

ข้อที่สี่คือ escalation หากผู้ดูแลคนแรกไม่ตอบรับ ระบบควรมีแผนสำรอง เช่น โทรแจ้งเตือน เพื่อไม่ให้เหตุการณ์ค้างอยู่เฉย ๆ

และข้อที่ห้าคือ low-cost เพราะถ้าระบบแพงหรือติดตั้งยาก ก็จะใช้จริงในบ้านทั่วไปได้ยาก

ดังนั้นโจทย์ของงานนี้ไม่ใช่แค่ทำโมเดลให้ accuracy สูง แต่ต้องออกแบบระบบที่เหมาะกับผู้สูงอายุ ผู้ดูแล และสภาพแวดล้อมจริงในบ้านครับ

จุดที่ต้องเน้น:

- Requirement ทั้ง 5 ข้อนี้จะถูกใช้เป็นเหตุผลว่าทำไมไม่เลือกกล้องหรือ wearable เป็นแกนหลัก
- คำว่า passive สำคัญมาก เพราะเป็นความต่างของระบบนี้

Transition:

ต่อไปมาดูว่าวิธีที่มีอยู่ใน literature และตลาดแบ่งได้เป็นกลุ่มไหน และแต่ละกลุ่มมี trade-off อย่างไรครับ

## Slide 5: วิธีที่มีอยู่ช่วยได้ แต่ยังมีข้อแลกเปลี่ยน

เวลา: 3:30 - 4:50

เป้าหมายของสไลด์: แสดงว่าได้ศึกษาทางเลือก ไม่ได้เลือก WiFi CSI โดยไม่มีเหตุผล

พูดตามนี้:

จาก literature review วิธีตรวจจับการล้มที่พบได้บ่อยแบ่งได้ประมาณ 4 กลุ่มครับ

กลุ่มแรกคือ wearable เช่น smart watch, pendant หรือ IMU ที่ติดกับร่างกาย จุดแข็งคือจับ motion จากตัวผู้ใช้โดยตรง เช่น acceleration หรือ orientation ของร่างกาย แต่ข้อจำกัดคือผู้สูงอายุต้องใส่จริง ต้องชาร์จแบต และตำแหน่งการใส่มีผลต่อความแม่นยำ ถ้าวันหนึ่งลืมใส่ ระบบก็จะไม่เห็นเหตุการณ์

กลุ่มที่สองคือ vision-based เช่น RGB camera หรือ depth camera จุดแข็งคือเห็น posture และเหตุการณ์ค่อนข้างชัด สามารถวิเคราะห์ภาพได้ละเอียด แต่ข้อจำกัดสำคัญคือ privacy รวมถึงปัญหามุมกล้อง แสง และการถูกบัง ถ้าล้มในมุมที่กล้องไม่เห็น ระบบก็อาจตรวจไม่ได้

กลุ่มที่สามคือ ambient sensors เช่น floor sensor, acoustic sensor หรือ PIR ข้อดีคือไม่ต้องสวมใส่ แต่ต้องติดตั้งเฉพาะจุด และ coverage อาจจำกัด เช่น sensor อยู่เฉพาะบางพื้นที่ ไม่ครอบคลุมทั้งบ้าน

กลุ่มสุดท้ายคือ radio-based sensing เช่น RSSI, CSI หรือ radar จุดแข็งคือ passive และ privacy-friendly กว่ากล้อง เพราะตรวจจากสัญญาณ ไม่ใช่ภาพ แต่ความท้าทายคือสัญญาณเปลี่ยนตามห้อง ตำแหน่งอุปกรณ์ จำนวนคน และสภาพแวดล้อม

สิ่งที่เราได้จากการเปรียบเทียบคือ ไม่มีวิธีไหนสมบูรณ์ทั้งหมด แต่ถ้า requirement คือไม่ใช้กล้อง ไม่ต้องสวมใส่ และต้นทุนต่ำ WiFi CSI เป็นทางเลือกที่ควรทดลองครับ

จุดที่ต้องเน้น:

- ทุกเทคโนโลยีมี trade-off
- WiFi CSI ไม่ใช่คำตอบที่ง่ายที่สุด แต่เข้ากับ requirement ของเรา

Transition:

ถ้ามองลึกลงไป ปัญหาของวิธีเดิมจำนวนมากไม่ใช่แค่เทคนิค แต่เป็น human factor ครับ

## Slide 6: ช่องว่างของวิธีเดิมอยู่ที่การใช้งานจริง

เวลา: 4:50 - 6:10

เป้าหมายของสไลด์: ทำให้กรรมการเห็นว่า accuracy อย่างเดียวไม่พอ ต้องคิดเรื่อง adoption และ workflow

พูดตามนี้:

ถ้ามองจากมุม usability หรือการใช้งานจริง วิธีเดิมมี human factor หลายอย่างที่ทำให้ระบบอาจล้มเหลวแม้ตัวเทคโนโลยีจะดีครับ

กล้องอาจตรวจ posture ได้ดี แต่การติดกล้องในพื้นที่ส่วนตัวทำให้ผู้สูงอายุหรือครอบครัวไม่สบายใจ ต่อให้ระบบไม่เก็บภาพ ก็ยังมี perception ว่าถูกเฝ้าดูอยู่

wearable เหมาะกับผู้ใช้ที่ยอมใส่และดูแลอุปกรณ์ได้ แต่ในกลุ่มผู้สูงอายุบางคนอาจลืมใส่ ถอดตอนนอน ถอดตอนอาบน้ำ หรือแบตหมด ซึ่งมักเป็นช่วงที่การล้มอาจเกิดได้

ปุ่ม SOS ใช้ง่ายและต้นทุนต่ำ แต่มีข้อจำกัดสำคัญคือผู้สูงอายุต้องมีสติและมีแรงพอที่จะกดปุ่ม ถ้าหมดสติ เจ็บมาก หรือเอื้อมไม่ถึง ระบบก็ไม่เกิด action

ambient sensors ไม่ต้องสวมใส่ แต่มีปัญหาเรื่อง coverage และตำแหน่งติดตั้ง ถ้าติดไม่ครอบคลุมพื้นที่จริง ก็ยังมี blind zone อยู่

ดังนั้น design target ของเราคือ ระบบที่ไม่บันทึกภาพ ไม่ต้องสวมใส่ และไม่ต้องรอให้ผู้สูงอายุเป็นคนเริ่ม action เอง ระบบควร detect เหตุการณ์ได้เอง แล้วส่งต่อให้ผู้ดูแลตัดสินใจครับ

จุดที่ต้องเน้น:

- ข้อจำกัดหลายอย่างเกิดจากพฤติกรรมมนุษย์ ไม่ใช่โมเดลอย่างเดียว
- ระบบที่ดีควรลดภาระของผู้สูงอายุ

Transition:

จาก requirement นี้ เราจึงเลือกศึกษาการใช้ WiFi CSI เป็น sensing layer ครับ

## Slide 7: เราจึงเลือก WiFi CSI เป็นตัวตรวจจับที่ไม่ใช้กล้อง

เวลา: 6:10 - 7:20

เป้าหมายของสไลด์: อธิบาย CSI แบบเข้าใจง่ายโดยไม่ลงสมการหนัก

พูดตามนี้:

WiFi CSI หรือ Channel State Information คือข้อมูลที่อธิบายสภาพของ channel ระหว่างตัวส่งและตัวรับ WiFi ครับ

ถ้าอธิบายแบบ intuition คือ ในห้องหนึ่ง สัญญาณ WiFi ไม่ได้เดินทางเป็นเส้นตรงอย่างเดียว แต่สะท้อนผนัง เฟอร์นิเจอร์ และร่างกายคน เกิดเป็น multipath หลายเส้นทาง

เวลาไม่มีคนเคลื่อนไหว pattern ของ channel จะค่อนข้างนิ่งในระดับหนึ่ง แต่เมื่อมีคนเดิน นั่ง เปลี่ยนท่า หรือเกิดการล้ม ร่างกายจะไปรบกวนเส้นทางของสัญญาณ ทำให้ค่า CSI เปลี่ยนไป

ข้อดีคือระบบไม่ได้เห็นภาพของผู้สูงอายุ แต่เห็นเพียงการเปลี่ยนแปลงของสัญญาณ ดังนั้นจึง privacy-friendly กว่ากล้อง และผู้สูงอายุไม่ต้องใส่อุปกรณ์ใด ๆ

ในงานนี้เราใช้ ESP32 เป็นอุปกรณ์รับ CSI เพราะมีต้นทุนต่ำและมีเครื่องมืออย่าง ESP32-CSI-Tool หรือ ESP-CSI ที่ช่วยให้สามารถสร้าง prototype ได้ โดยไม่ต้องใช้อุปกรณ์ WiFi sensing ราคาแพงเหมือนงานวิจัยบางกลุ่มในอดีต

จุดที่ต้องเน้น:

- “ไม่เห็นภาพคน เห็นแค่ signal pattern”
- CSI เหมาะกับ privacy-first sensing แต่ยังต้องจัดการปัญหา environment variation

ถ้ากรรมการถาม:

- CSI ต่างจาก RSSI อย่างไร: RSSI เป็นค่าความแรงสัญญาณรวม ๆ ค่าเดียวหรือไม่กี่ค่า แต่ CSI ให้รายละเอียดในระดับ subcarrier มากกว่า จึงใช้แยก pattern การเคลื่อนไหวได้ละเอียดกว่า

Transition:

เมื่อรับ CSI มาแล้ว เราต้องแปลงสัญญาณให้เป็นข้อมูลที่โมเดลใช้ได้ครับ

## Slide 8: สัญญาณ WiFi ถูกแปลงเป็นคุณลักษณะก่อนเข้าโมเดล

เวลา: 7:20 - 8:30

เป้าหมายของสไลด์: อธิบาย feature extraction ให้กรรมการเข้าใจว่าจากสัญญาณดิบไปเป็น input model ได้อย่างไร

พูดตามนี้:

Pipeline ของข้อมูลเริ่มจาก ESP32 รับ CSI packet ต่อเนื่อง แต่เราไม่ได้ส่ง raw packet ทั้งหมดเข้าโมเดลโดยตรงครับ เพราะข้อมูลดิบมีขนาดใหญ่ มี noise และไม่เหมาะกับการประมวลผลแบบ real-time ในต้นแบบ

แนวทางของเราคือรวม CSI เป็น window แล้วคำนวณ feature จากข้อมูลใน window นั้น ใน code ปัจจุบัน preprocessing parse ข้อมูล CSI ออกมาเป็น 52 subcarriers

จากนั้นในแต่ละ subcarrier จะคำนวณค่าสถิติ 8 ค่า เช่น mean, min, max, standard deviation, MAD, IQR, skewness และ kurtosis

ดังนั้น 52 subcarriers คูณ 8 statistics จะได้ feature vector จำนวน 416 ค่า ต่อหนึ่ง window

เหตุผลที่ทำเป็น feature vector คือทำให้ข้อมูล compact ขึ้น ลดภาระการประมวลผล และเหมาะกับโมเดลที่ต้องการตอบผลเร็ว เช่น Random Forest ใน active inference ปัจจุบัน

พูดอีกแบบคือ เราไม่ได้ให้โมเดลดูสัญญาณยาวทั้งหมด แต่ให้โมเดลดู “สรุปลักษณะของสัญญาณช่วงล่าสุด” แล้วตัดสินว่า pattern นี้ใกล้เคียง fall หรือ no_fall ครับ

จุดที่ต้องเน้น:

- 52 subcarriers x 8 stats = 416 features
- Feature extraction เป็นสะพานระหว่าง hardware signal กับ ML model

Transition:

ต่อไปจะดูว่างานวิจัยที่ผ่านมาสนับสนุนแนวคิด WiFi CSI สำหรับ fall detection อย่างไรครับ

## Slide 9: งานวิจัยยืนยันว่า WiFi CSI ตรวจจับการล้มได้

เวลา: 8:30 - 10:00

เป้าหมายของสไลด์: สรุป literature ที่เกี่ยวกับ fall detection โดยเน้นสิ่งที่เรียนรู้ ไม่ไล่ paper ทีละบรรทัด

พูดตามนี้:

ใน literature มีงานหลายกลุ่มที่สนับสนุนแนวคิด device-free fall detection ด้วย WiFi CSI ครับ

ตัวอย่างเช่น WiFall ใช้ CSI เป็น indicator ของกิจกรรม และเสนอว่าการตรวจจับการล้มโดยไม่ต้องสวมใส่อุปกรณ์สามารถทำได้ เพราะการล้มทำให้ pattern ของสัญญาณเปลี่ยนต่างจากกิจกรรมทั่วไป

งานอย่าง Anti-Fall และ RT-Fall ใช้ทั้ง amplitude และ phase ของ CSI เพื่อแยก fall ออกจาก fall-like activity เช่น การนั่งลงเร็ว หรือการเปลี่ยนท่าทางที่รุนแรง โดยให้ความสำคัญกับ real-time และ contactless detection

สิ่งที่เราเรียนรู้จากงานเหล่านี้มี 2 ด้านครับ ด้านแรกคือ CSI มีข้อมูลที่สัมพันธ์กับการเคลื่อนไหวจริง และสามารถใช้ตรวจจับการล้มได้ในสภาพแวดล้อมที่ออกแบบการทดลองไว้

แต่อีกด้านหนึ่งคือหลายงานทดลองใน environment ที่ควบคุมไว้ เช่น ห้องเดิม ตำแหน่งอุปกรณ์เดิม หรือผู้ทดสอบกลุ่มเดิม เมื่อนำไปใช้จริงอาจเจอ domain shift เช่น เปลี่ยนห้อง เปลี่ยนมุมวาง ESP32 มีเฟอร์นิเจอร์เพิ่ม หรือมีหลายคนในพื้นที่

ดังนั้นเราไม่ได้ใช้ literature เพื่อบอกว่า “ใช้ได้แน่นอนทุกบ้าน” แต่ใช้เพื่อบอกว่า signal มีศักยภาพ และงานของเราต้องต่อยอดด้วย validation ในสภาพแวดล้อมจริงครับ

จุดที่ต้องเน้น:

- Related work สนับสนุน feasibility
- แต่ต้องระวัง domain shift และ unseen test

ถ้ากรรมการถาม:

- ถ้าถามว่าทำไมไม่ใช้ paper เดียวเป็น base: ตอบว่าแต่ละ paper มี setup ต่างกัน เราจึงใช้เป็นแนวทาง แต่ implementation ต้องปรับตามอุปกรณ์ ESP32 และระบบแจ้งเตือนของเรา

Transition:

นอกจากงานตรวจจับการล้มแล้ว ยังมีงานฝั่ง ESP32 และ Human Activity Recognition ที่ช่วยให้ prototype ทำได้ต้นทุนต่ำขึ้นครับ

## Slide 14: เราเก็บ CSI ผ่าน USB serial เพื่อให้ข้อมูลนิ่งขึ้น

เวลา: 14:40 - 15:50

เป้าหมายของสไลด์: อธิบายเหตุผลเชิงวิศวกรรมของ data collection mode ปัจจุบัน

พูดตามนี้:

ในช่วงแรกของการทดลอง เราพิจารณาการส่งข้อมูลผ่าน UDP หรือ hotspot ด้วย แต่สำหรับ data collection ปัจจุบันเราเลือก USB serial mode เพราะควบคุมสภาพแวดล้อมได้มากกว่า

โครงสร้างคือ ESP32 ตัว receiver สร้าง CSI network และรับ packet จาก ESP32 ตัว sender ตัว sender ส่ง packet ต่อเนื่องเพื่อให้ receiver วัด CSI ได้สม่ำเสมอ จากนั้น receiver ส่งข้อมูล CSI ออกผ่าน USB serial ที่ baud rate 921600 เข้าเครื่องคอมพิวเตอร์

ข้อดีของแนวทางนี้คือไม่ต้องพึ่ง hotspot หรือ router ภายนอก ลดปัญหา IP เปลี่ยน firewall หรือ client isolation และช่วยให้เราตรวจ raw CSI ได้ง่ายระหว่างพัฒนา

หลังจากเก็บข้อมูลแล้ว pipeline จะ parse CSI, extract feature 416 ตัว แล้วนำไปใช้ train หรือ inference ต่อ

อย่างไรก็ตาม สำหรับ deployment จริง แนวทางต่อไปคือให้ receiver ESP32 ส่ง feature หรือ CSI window ขึ้น cloud ผ่าน WiFi โดยตรง และอาจใช้ BLE provisioning ให้ผู้ใช้ตั้งค่า WiFi ผ่านแอปได้ ซึ่งจะลดการพึ่งพาคอมพิวเตอร์ในบ้านครับ

จุดที่ต้องเน้น:

- USB serial เป็นโหมด data collection / prototype ไม่ใช่ภาพสุดท้ายของ production
- Production path คือ cloud upload จาก ESP32 receiver

ถ้ากรรมการถาม:

- ถ้าถามว่าทำไมไม่ส่ง cloud เลย: ตอบว่าเริ่มจาก serial เพื่อควบคุม data quality ก่อน เมื่อ pipeline และ model เสถียรขึ้นจึงย้ายไป cloud upload

Transition:

## Slide 15: ผลทดสอบกับชุดข้อมูลเดิมดี แต่ยังต้องพิสูจน์ในสถานการณ์จริง

## Slide 22: ข้อจำกัดสำคัญคือความแม่นยำเมื่อเปลี่ยนสภาพแวดล้อม

เวลา: 23:00 - 23:40

เป้าหมายของสไลด์: พูด limitation ก่อนกรรมการถาม แสดงความเข้าใจ risk ทั้ง ML และ system

พูดตามนี้:

ข้อจำกัดที่ต้องพูดตรง ๆ มี 4 เรื่องครับ

ข้อแรกคือ domain shift โมเดลอาจเรียนรู้ pattern ที่ผูกกับห้อง มุมวาง ESP32 คนที่ใช้ train หรือสภาพแวดล้อมเดิมมากเกินไป เมื่อเปลี่ยนห้องหรือเปลี่ยนคน performance อาจลดลง

ข้อที่สองคือ false alarm กิจกรรมที่คล้ายการล้ม เช่น นั่งลงเร็ว ก้มเก็บของ หรือวางของแรง ๆ อาจทำให้สัญญาณเปลี่ยนแรงและกระตุ้นระบบได้

ข้อที่สามคือ system durability ตอนนี้ escalation timer และ cooldown ยังอยู่ใน memory ซึ่งพอสำหรับ demo แต่ไม่พอสำหรับ production เพราะถ้า server restart timer จะหาย

ข้อที่สี่คือ configuration และ security หลายค่าใน mobile/backend ยังเป็น development config เช่น API URL, API key และ Supabase config ต้องย้ายไป env/config และจัดการ secret ก่อน deploy จริง

ดังนั้นในการนำเสนอนี้ผมจะแยกให้ชัดว่าอะไรคือ demo, อะไรคือ offline metric และอะไรคือ real-world validation ที่ต้องทำต่อครับ

จุดที่ต้องเน้น:

- พูด limitation อย่างมั่นใจ ไม่ต้องหลบ
- แยก ML risk กับ system risk

ถ้ากรรมการถาม:

- ถ้าถามว่า false alarm มากแค่ไหน: ตอบว่ายังต้องวัดด้วย unseen test และ fall-like scenario ไม่ควร claim ตัวเลขก่อนทดสอบ

Transition:

จาก limitation เหล่านี้ แผนงานต่อไปจึงต้องเน้นการพิสูจน์ความน่าเชื่อถือครับ
