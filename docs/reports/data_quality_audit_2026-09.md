# ตรวจคุณภาพข้อมูล — ข้อมูลที่เก็บมาใช้ได้จริงไหม

**วันที่:** 2026-09-01
**สคริปต์:** `fall_detection_backend/ml_service/experiments/audit_data.py` (รันซ้ำได้)
**ข้อมูลที่ตรวจ:** `data/processed_v2` — 2,412 window · 804 ไฟล์บันทึก

---

## คำตอบสั้น

**ข้อมูลไม่ใช่ garbage แต่ตัวเลข 95.6% ไม่ได้มาจากการตรวจจับการล้ม**

โมเดลแยก fall ออกจาก non_fall ได้เพราะ **ระดับสัญญาณเฉลี่ยของแต่ละ subcarrier ต่างกัน**
ซึ่งเป็นลักษณะของสภาพห้องตอนบันทึก ไม่ใช่ลักษณะของการเคลื่อนไหว

สัญญาณของการเคลื่อนไหวจริงมีอยู่ แต่อ่อนกว่ามาก — วัดได้ประมาณ **72.6%** ไม่ใช่ 95.6%

**ข้อมูลชุดนี้ยังใช้ต่อได้ในฐานะ pilot แต่ใช้ยืนยันว่า "ระบบตรวจจับการล้มได้" ไม่ได้**

---

## หลักฐาน

### [1] ข้อมูลดิบสะอาด

```
NaN 0 · Inf 0 · แถวซ้ำเป๊ะ 0 · feature ค่าคงที่ 40/416
```

40 feature ที่ค่าคงที่คือ subcarrier ที่เป็น guard band ของ WiFi (ไม่มีข้อมูลอยู่แล้ว) ปกติ
ไม่ใช่ปัญหา แต่ควรตัดออกตอน preprocess

### [2] ⚠️ เก็บข้อมูลเป็นบล็อก — คลาสกับ session ทับกันสนิท

```
ไฟล์ทั้งหมด 804 · สลับคลาส 1 ครั้ง
```

เรียงตาม `file_id` แล้วได้ `[0,0,0,...,0,1,1,1,...,1]` — **บันทึก fall ทั้งหมดก่อน แล้วค่อยบันทึก
non_fall ทั้งหมด** ไม่ได้สลับกันเลย

ผลคือ **ทุกอย่างที่ต่างกันระหว่างสองช่วงเวลานั้นกลายเป็นตัวทำนายคลาสที่สมบูรณ์แบบ** —
ตำแหน่ง ESP32 ขยับ, เฟอร์นิเจอร์ย้าย, คนในห้อง, อุณหภูมิ, gain ที่ต่างกันหลัง reboot,
เวลาของวัน ทั้งหมดนี้แยกไม่ออกจาก "การล้ม" ด้วยข้อมูลชุดนี้

นี่ไม่ใช่ปัญหาของโมเดล แต่เป็นปัญหาของ**วิธีเก็บ** และ**ไม่มีวิธีวิเคราะห์ใดแก้ย้อนหลังได้**

### [3] สภาพห้องเปลี่ยนไปจริงระหว่าง session

ทดสอบภายในคลาสเดียวกัน โดยให้ทายว่าไฟล์นั้นเก็บช่วงต้นหรือช่วงท้ายของ session

| ภายในคลาส | ทายได้แม่น |
|---|---|
| non_fall | **88.0%** |
| fall | 64.2% |

**88% ภายในคลาสเดียวกัน** แปลว่า feature จำได้ชัดเจนว่าไฟล์นั้นบันทึกตอนไหน
ทั้งที่เป็นการกระทำแบบเดียวกันหมด — สภาพ RF ในห้องเลื่อนไปเรื่อย ๆ ระหว่างการเก็บ

เมื่อ drift ระดับนี้มีอยู่ และคลาสถูกเก็บแยกช่วงกัน สิ่งที่โมเดลเรียนได้ง่ายที่สุดคือ drift

### [4] เกณฑ์ตัดเดียวบน subcarrier เดียวได้ 84%

```
#56 (subcarrier  7, mean)  →  84.2%
#48 (subcarrier  6, mean)  →  84.1%
#72 (subcarrier  9, mean)  →  82.7%
```

**5 อันดับแรกเป็น `mean` ทั้งหมด** — ค่าเฉลี่ยความแรงสัญญาณ

การล้มเป็นเหตุการณ์ชั่วขณะที่ทำให้สัญญาณ**แกว่ง** ถ้าโมเดลจับการล้มจริง feature ที่ควรเด่นคือ
`std`, `mad`, `iqr` ไม่ใช่ `mean` การที่ค่าเฉลี่ยของ subcarrier เดียวแยกได้ 84% บอกว่า
สองคลาสนี้อยู่ในสภาพแวดล้อมที่ต่างกันตั้งแต่ต้น

### [5] ✓ วิธีวัดไม่มีปัญหา

```
สลับ label แบบสุ่มระดับไฟล์ → acc 48.2%
```

ได้ราว 50% ตามที่ควร — harness กับ grouped split ทำงานถูกต้อง ตัวเลข 95.6% ไม่ได้มาจากบั๊ก
ในโค้ดประเมินผล แต่มาจากตัวข้อมูลเอง

### [6] ตัวเลขแตกออกเป็น 2 ส่วนชัดเจน

| ใช้ feature กลุ่มไหน | Accuracy | Fall recall |
|---|---|---|
| ครบทุก feature | 95.6% | 96.6% |
| **เฉพาะระดับสัญญาณ** (mean/min/max) | **95.6%** | 96.2% |
| **เฉพาะความแปรปรวน** (std/mad/iqr/skew/kurt) | **72.6%** | 75.8% |

**ใช้แค่ระดับสัญญาณอย่างเดียวได้เท่ากับใช้ทุก feature** — ความแปรปรวนไม่ได้เพิ่มอะไรเลย

น้ำหนักที่ RandomForest ให้:
```
mean   56.9%  ████████████████████████████████████████████████████████
min    20.1%  ████████████████████
max    11.1%  ███████████
std     2.2%  ██
mad     2.2%  ██
iqr     1.8%  █
skew    3.6%  ███
kurt    2.2%  ██
```

**88% ของน้ำหนักอยู่ที่ระดับสัญญาณ · 12% อยู่ที่ความแปรปรวน**

## แปลผล

| ตัวเลข | ความหมายจริง |
|---|---|
| 97.9% (รายงานเดิม) | วัดด้วย split ที่ข้อมูลรั่ว + sequence ข้ามไฟล์ |
| 95.6% (grouped split) | แยก session ที่บันทึก fall ออกจาก session ที่บันทึก non_fall |
| **72.6%** (เฉพาะความแปรปรวน) | **ใกล้เคียงความสามารถจริงในการจับการเคลื่อนไหวมากที่สุด** |

72.6% ยังสูงกว่าเดา (50%) อย่างมีนัยสำคัญ — **มีสัญญาณของการล้มอยู่จริงใน CSI**
แค่ถูกกลบด้วย confound ที่แรงกว่า

## สิ่งที่ต้องทำตอนเก็บ unseen data — สำคัญที่สุดในเอกสารนี้

ถ้าเก็บชุดใหม่ด้วยวิธีเดิม จะได้ข้อมูลที่มีปัญหาเดิมซ้ำอีกชุด

### 1. สลับคลาสภายใน session เดียวกัน — ข้อนี้สำคัญที่สุด

```
❌ แบบเดิม   ล้ม ×400 (วันจันทร์)  แล้วค่อย  ไม่ล้ม ×404 (วันอังคาร)
✅ แบบใหม่   ล้ม → ไม่ล้ม → ล้ม → ไม่ล้ม  สลับกันใน session เดียว ไม่ขยับอะไรเลย
```

สภาพห้องจะเหมือนกันทั้งสองคลาส หักล้างกันเอง เหลือแต่ความต่างที่มาจากการเคลื่อนไหวจริง

### 2. บันทึก metadata ทุกไฟล์

วันเวลา · ตำแหน่ง ESP32 · ใครเป็นคนแสดง · ห้องไหน — ต้องตรวจ confound ย้อนหลังได้
ตอนนี้มีแค่ `file_id` เรียงตามลำดับเท่านั้น

### 3. อย่า reboot / อย่าขยับ ESP32 ระหว่าง session

reboot ทีเดียว gain เปลี่ยน ระดับสัญญาณเลื่อนทั้งชุด

### 4. เก็บหลาย session หลายห้อง แล้วแบ่ง test ตาม session

test set ต้องเป็น session ที่โมเดลไม่เคยเห็นเลย ไม่ใช่แค่ไฟล์ที่ไม่เคยเห็น
นี่คือสิ่งที่ mentor ขอจริง ๆ เมื่อพูดว่า "unseen scenario"

### 5. เพิ่ม feature ที่ทน drift

ระดับสัญญาณดิบอ่อนไหวต่อสภาพห้องมาก ควรพิจารณา
- normalize ต่อ subcarrier ด้วย baseline ของ session นั้น
- ใช้ **ความเปลี่ยนแปลงตามเวลา** (ผลต่างระหว่าง packet ติดกัน) แทนค่าสัมบูรณ์
- ตัด 40 subcarrier ที่เป็น guard band ออก
