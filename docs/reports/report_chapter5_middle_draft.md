# บทที่ 5
# สรุปผลและข้อเสนอแนะ

> หมายเหตุสำหรับผู้เขียน (ลบออกก่อนรวมเล่ม): ส่วนที่มีเครื่องหมาย ⟪รอเติม⟫ รอผลทดสอบสดกับบอร์ดจริงและการย้ายตำแหน่งบอร์ด · ห้ามใส่ค่าคาดการณ์จากสไลด์
> ตรวจสถานะกับโค้ดจริง ณ วันที่ 25 พฤศจิกายน 2569 — ถ้าทำส่วนที่ค้างเสร็จก่อนส่งเล่ม ให้ย้ายจากข้อเสนอแนะขึ้นไปไว้ในสรุปผล

## สรุปผลการดำเนินงาน

โครงการนี้พัฒนาระบบต้นแบบสำหรับตรวจจับการล้มของผู้สูงอายุด้วยข้อมูล WiFi CSI จากบอร์ด ESP32 ร่วมกับบริการ Machine Learning, Backend API, ฐานข้อมูล และแอปพลิเคชัน Middle สำหรับแจ้งเตือนผู้ดูแล โดยไม่ต้องใช้กล้องและไม่ต้องให้ผู้สูงอายุสวมอุปกรณ์ เมื่อเทียบกับวัตถุประสงค์ของโครงการในบทที่ 1 สรุปผลได้ดังนี้

1. **ระบบตรวจจับการล้มด้วย WiFi CSI จาก ESP32** พัฒนาอุปกรณ์ตรวจจับด้วย ESP32 จำนวน 2 ตัวที่รับข้อมูล CSI ได้ 98–100 packet ต่อวินาทีอย่างสม่ำเสมอผ่าน USB Serial พร้อมเครื่องมือเก็บข้อมูลแบบหน้าเว็บ และเก็บชุดข้อมูลรอบที่สองจากผู้แสดง 5 คน รวม 801 ไฟล์ นอกจากนี้ firmware รองรับการตั้งค่า WiFi ผ่าน BLE สำหรับการใช้งานจริงแล้ว แต่ยังไม่ได้ทดสอบจนครบขั้นตอนกับบอร์ดจริง

2. **โมเดลเรียนรู้ของเครื่องสำหรับจำแนกการล้ม** พัฒนาบริการ Machine Learning ด้วย FastAPI ที่รองรับโมเดล Random Forest 2 รุ่น และเครื่องมือตรวจจับแบบสด โมเดลที่ใช้ได้ความแม่นยำกับผู้แสดงที่โมเดลไม่เคยเห็น (unseen) 87.1% เพิ่มจากตัวเก่า 72.4% ด้วย feature ความเร็วการเคลื่อนไหวและข้อมูลหลังเหตุการณ์ 1.5 วินาที ผลดีขึ้นกับผู้แสดงทุกคน (84–90%) และตรวจสอบแล้วว่าไม่ได้เกิดจากความบังเอิญ ส่วนการตรวจจับแบบต่อเนื่องจับการล้มได้ 64.2% โดยไม่แจ้งผิดในข้อมูลกิจวัตร 8.5 นาที ⟪รอเติม: ผลทดสอบสด⟫

3. **Backend API** พัฒนา Express API ที่รับข้อมูลจากอุปกรณ์ เรียกใช้บริการ Machine Learning บันทึกเหตุการณ์ ส่ง Push Notification และจัดการการยกระดับการแจ้งเตือน มีการแยก API key ตามขอบเขตการใช้งาน ตรวจตัวตนและความเป็นสมาชิกบ้านของผู้กดรับทราบ ส่ง Push Notification เฉพาะสมาชิกของบ้านที่เกิดเหตุ API และหน้าเว็บสำหรับผู้ดูแลระบบที่เห็นภาพรวม เหตุการณ์ และอุปกรณ์ทุกบ้าน และเอกสาร API ที่ตรวจความถูกต้องอัตโนมัติ ชุดทดสอบอัตโนมัติ 184 กรณีผ่านทั้งหมด

4. **แอปพลิเคชัน Middle สำหรับผู้ดูแล** พัฒนาแอปพลิเคชัน 33 หน้าจอ ผู้ดูแลรับ Push Notification ดูรายการแจ้งเตือนแยกตามบ้านพร้อมเวลาที่เหลือจริงก่อนระบบโทร และกดยืนยันรับทราบได้ มีระบบบัญชีผู้ใช้ด้วยเบอร์โทรศัพท์และรหัสผ่าน บทบาทเจ้าของบ้านและผู้ดูแล การเชิญสมาชิกเข้าบ้านด้วยรหัสหรือ QR Code ประวัติการเปลี่ยนแปลงที่ฐานข้อมูลบันทึกเองและแก้ไขไม่ได้ และขั้นตอนเพิ่มอุปกรณ์ผ่าน BLE สิทธิ์การเข้าถึงข้อมูลของแต่ละบ้านบังคับที่ฐานข้อมูล และเปิดใช้บนฐานข้อมูลจริงแล้วเมื่อวันที่ 23 พฤศจิกายน 2569 ทั้งนี้ทดสอบบนแอปพลิเคชันเวอร์ชันเว็บ ยังไม่ได้ทดสอบบนสมาร์ตโฟนจริงหลังเปิดระบบบัญชี

5. **กลไกการแจ้งเตือนต่อเนื่อง** เมื่อไม่มีผู้ดูแลกดรับทราบภายใน 60 วินาที ระบบโทรแจ้งเตือนผ่าน Twilio ได้ ตัวจับเวลากู้คืนได้เมื่อบริการเริ่มใหม่ และพัฒนาการโทรด้วยข้อความภาษาไทยที่ร่างโดย AI ซึ่งระบุห้องและบ้านของเหตุการณ์ โดยการตัดสินใจโทรยังเป็นแบบกฎทั้งหมด และถอยกลับไปใช้ข้อความมาตรฐานเมื่อ AI ขัดข้อง ทดสอบการโทรจริงแล้ว และทดสอบครบเส้นทางบนฐานข้อมูลจริงเมื่อวันที่ 24 พฤศจิกายน 2569 ตั้งแต่บันทึกเหตุการณ์ การ์ดแจ้งเตือนในแอป จนถึงการโทรและส่ง SMS เมื่อครบ 60 วินาที

## ปัญหาและอุปสรรค

1. **ข้อมูลชุดแรกมีปัจจัยแฝงจากช่วงเวลาที่เก็บ** ชุดข้อมูลแรกเก็บท่าล้มทั้งหมดก่อนแล้วจึงเก็บท่าที่ไม่ใช่การล้ม ทำให้สภาพแวดล้อมของห้องในแต่ละช่วงเวลาสัมพันธ์กับประเภทของข้อมูล โมเดลจึงสามารถแยกข้อมูลได้จากความต่างของช่วงเวลาแทนการจับลักษณะการล้ม ผู้พัฒนาจึงออกแบบการเก็บข้อมูลรอบที่สองใหม่ให้สลับท่าภายในรอบเดียวกันและแบ่งข้อมูลทดสอบตามผู้แสดง

2. **คุณภาพลิงก์สัญญาณระหว่างการเก็บข้อมูล** การเก็บข้อมูลรอบที่สองพบสัญญาณรบกวนสูงตลอดทุกรอบ ซึ่งส่งผลต่อคุณภาพของข้อมูลแม้อัตราการรับข้อมูลจะครบ feature แบบเดิมจึงทำนายผู้แสดงที่ไม่เคยเห็นได้เพียง 54.5% ใกล้เคียงการเดา ผู้พัฒนาแก้โดยออกแบบ feature แบบเหตุการณ์ที่ปรับตามระดับสัญญาณรบกวนของแต่ละไฟล์ได้ 72.9% แล้วเพิ่ม feature ความเร็วการเคลื่อนไหวและข้อมูลหลังเหตุการณ์จนได้ 87.1%

3. **อัตราและความต่อเนื่องของข้อมูล CSI** firmware รุ่นแรกให้อัตราข้อมูลต่ำกว่าที่ตั้งไว้ และการส่งข้อมูลผ่าน WiFi แบบ UDP ขาดเป็นช่วงจากการสแกน WiFi ของระบบปฏิบัติการคอมพิวเตอร์ แก้ไขด้วยการปรับ firmware และเปลี่ยนไปใช้ USB Serial

4. **ข้อผิดพลาดที่ไม่แสดงอาการ** ระหว่างการพัฒนาพบข้อผิดพลาดที่ระบบไม่แจ้งเตือน เช่น ปุ่มรับทราบส่งรหัสผิดตัวทำให้ระบบยังโทรแจ้งเตือนทั้งที่ผู้ดูแลกดแล้ว การนับถอยหลังที่เริ่มใหม่ทุกครั้งที่เปิดแอปพลิเคชันจนแสดงเวลาเหลือมากกว่าความจริง และหน้าตั้งค่าอุปกรณ์บันทึกค่าปลอมเมื่อข้อมูลไม่ครบ ผู้พัฒนาจึงแจ้งผู้ใช้ทุกครั้งที่บันทึกไม่สำเร็จ ตรวจผลลัพธ์ของการบันทึกข้อมูลรวมถึงกรณีที่ฐานข้อมูลปฏิเสธตามสิทธิ์โดยไม่มีข้อความผิดพลาด และเขียนชุดทดสอบครอบคลุมกรณีเหล่านี้

5. **คีย์ที่ฝังในแอปพลิเคชันไม่ใช่การยืนยันตัวตน** คีย์ของแอปพลิเคชันแกะออกจากไฟล์ติดตั้งได้ ในช่วงแรกผู้ที่มีคีย์จึงกดรับทราบแทนบ้านอื่นได้ ซึ่งเท่ากับยกเลิกการโทรฉุกเฉินของบ้านนั้น และ Push Notification ถูกส่งไปทุกเครื่อง ผู้พัฒนาแก้โดยให้ Backend ตรวจ token ของบัญชีผู้ใช้และความเป็นสมาชิกบ้านทุกครั้ง และส่ง Push เฉพาะสมาชิก

6. **ข้อจำกัดของฮาร์ดแวร์ ESP32** การเพิ่ม BLE provisioning ต้องขยายพื้นที่โปรแกรม และในโหมดใช้งานจริงที่ ESP32 ทำงานเป็นทั้ง Access Point และ Station ช่องสัญญาณจะถูกกำหนดตามเราเตอร์ของบ้าน ซึ่งต่างจากช่องสัญญาณคงที่ที่ใช้ตอนเก็บข้อมูลฝึกโมเดล

7. **การนำระบบไปใช้ในบ้านจริง** ระบบต้นแบบยังต้องใช้คอมพิวเตอร์ในพื้นที่สำหรับรับข้อมูล CSI จาก ESP32 และยังไม่มีเส้นทางที่ส่งข้อมูล CSI จากบ้านผู้ใช้ขึ้นระบบคลาวด์โดยตรง

8. **ฐานข้อมูลจริงไม่ตรงกับ schema** ตารางบางตารางบนฐานข้อมูลจริงถูกสร้างไว้ก่อน schema รุ่นปัจจุบัน คำสั่งสร้างตารางแบบ "ถ้ายังไม่มี" จึงข้ามไปโดยไม่มีข้อความเตือน ทำให้บันทึกเหตุการณ์การล้มไม่ได้และการ์ดในแอปค้างสถานะ ปัญหานี้พบในการทดสอบครบเส้นทางครั้งแรก และแก้ไขแล้วพร้อมเพิ่มการตรวจโครงสร้างในสคริปต์ตรวจความพร้อม

9. **การทดสอบ Push Notification บน iPhone** แอปพลิเคชันที่ build เองต้องลงนามด้วยบัญชี Apple Developer แบบเสียค่าใช้จ่ายจึงจะรับ Push ได้ และแอป Expo Go รุ่นปัจจุบันไม่รองรับโปรเจกต์รุ่นนี้ การทดสอบบน iPhone จึงทำผ่านแอปเวอร์ชันเว็บซึ่งแสดงการ์ดแจ้งเตือนได้แต่ไม่มี Push

## ข้อเสนอแนะและแนวทางการพัฒนาต่อ

1. **ส่งข้อมูล CSI ขึ้นระบบคลาวด์โดยไม่ต้องมีคอมพิวเตอร์ในบ้าน** ให้อุปกรณ์ส่งข้อมูลหรือ feature ขึ้น Backend API ผ่าน WiFi ของบ้านโดยตรง และผ่านขั้นตอนบันทึกเหตุการณ์และแจ้งเตือนตามปกติ

2. **ขยายชุดข้อมูลและสภาพแวดล้อมการทดสอบ** เพิ่มจำนวนผู้แสดง ห้อง ตำแหน่งการวางอุปกรณ์ และทดสอบว่าโมเดลทำงานได้เมื่อช่องสัญญาณ WiFi ต่างจากตอนฝึก รวมถึงเพิ่มข้อมูลกิจวัตรต่อเนื่องให้ยาวขึ้นเพื่อวัดอัตราการแจ้งผิดต่อชั่วโมงได้แม่นยำขึ้น ท่าที่ควรเพิ่มข้อมูลคือการล้มไปด้านข้างซึ่งยังตรวจจับยากที่สุด และกรณีที่มีหลายคนในห้องหรือของชิ้นใหญ่ล้ม ⟪รอเติม: ข้อเสนอเพิ่มเติมจากผลทดสอบสด⟫

3. **ทดสอบการตั้งค่า WiFi ผ่าน BLE กับบอร์ดจริงให้ครบขั้นตอน** และกำหนดขั้นตอนการผลิตรหัสอุปกรณ์และรหัสจับคู่ที่ไม่ซ้ำกันในแต่ละเครื่อง เนื่องจากรหัสจับคู่ที่สั้นหรือซ้ำกันทำให้ถูกเดาได้

4. **ทดสอบระบบบัญชีผู้ใช้และ Push บนสมาร์ตโฟนจริง** ระบบบัญชีและการแยกสิทธิ์ตามบ้านเปิดใช้บนฐานข้อมูลจริงแล้ว แต่ยังทดสอบผ่านแอปเวอร์ชันเว็บ ควรทดสอบบนสมาร์ตโฟน Android และ iPhone จริง รวมถึงการกดรับทราบเพื่อยกเลิกการโทรจากสมาร์ตโฟน

5. **เพิ่มความสามารถของระบบบัญชีผู้ใช้** เช่น การยืนยันเบอร์โทรศัพท์และการตั้งรหัสผ่านใหม่ด้วยรหัส OTP ทาง SMS ซึ่งต้องใช้ผู้ให้บริการ SMS ที่ส่งถึงหมายเลขในประเทศไทยได้

6. **ประเมิน AI call ก่อนขยายบทบาท** เก็บสถิติสัดส่วนการโทรที่ใช้ข้อความจาก AI เทียบกับข้อความมาตรฐาน และทดสอบแบบเงา (shadow mode) ก่อนพิจารณาให้ AI มีส่วนช่วยตัดสินใจลดการแจ้งเตือนผิด

7. **นำระบบขึ้นใช้งานบนคลาวด์** ระบบมีไฟล์สำหรับ deploy บน Render แล้ว ควรทดสอบการทำงานบนคลาวด์ร่วมกับฐานข้อมูลจริงก่อนนำไปทดลองใช้งานกับผู้ใช้
