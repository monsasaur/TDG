## ทางรับข้อมูล: USB Serial ✅ ใช้ทางนี้ (เปลี่ยนจาก UDP 2026-11-11 บ่าย)

#1 เสียบสาย USB กับแมคตลอด · แมคเกาะ WiFi บ้านได้ปกติ (ใช้ 5GHz) · ไม่ต้องใช้ iPhone

**ทำไมเลิก UDP:** ขา #1 → แมคทาง WiFi ขาดเป็นพัก ๆ (วัด 40 วิ: ต่ำสุด 24 pkt/s · 8/20 ครั้งต่ำกว่า 90 ·
#1 ส่งพลาดถึง 46/วิ) — macOS สแกนหา WiFi อื่นเป็นระยะ (โดยเฉพาะตอนเกาะ WiFi ที่ไม่มีเน็ต) วิทยุออกจาก
ช่อง 6 ไป ~1-2 วิ แก้จากฝั่งเราไม่ได้ · serial วัดได้ **98-100 pkt/s ไม่ตกเลย** (ใช้สายแค่ 52% ที่ 921600 baud)

firmware serial (`active_ap/build_serial`) ส่งผ่านคิว + task แยกเหมือน UDP: ไม่บล็อก WiFi · กรอง MAC #2 ·
ทิ้งเฟรมที่ #2 ส่งซ้ำ (rx_seq) · บรรทัด `STAT` ทุก 1 วิ (`dest=serial`) → หน้าเว็บแสดงตัวนับของ #1 เหมือนเดิม

```bash
# flash #1 (เช็ค MAC ก่อน ต้อง ...6a:b8)
. ~/esp/esp-idf-v5.4/export.sh && cd fall_detection_backend/ESP32-CSI-Tool/active_ap
idf.py -B build_serial -D SDKCONFIG=build_serial/sdkconfig \
    -D SDKCONFIG_DEFAULTS="sdkconfig.datacollect.defaults" -p /dev/cu.usbserial-0001 build flash

# เก็บ — โหมด serial เป็นค่าเริ่มต้น (ไม่ต้องตั้ง CSI_TRANSPORT)
cd ../../ml_service && caffeinate -i python data_collection/collect_web.py
```

⚠️ **เปิดพอร์ต USB ทุกครั้ง #1 จะรีบูต** — เปิดหน้าเว็บก่อน แล้วค่อยนับเวลาอุ่นบอร์ด 10-15 นาที
⚠️ ห้ามรัน `idf.py monitor` / สคริปต์อื่นที่เปิดพอร์ตเดียวกันระหว่างเก็บ
⚠️ แมคต้องเสียบสายชาร์จ · รันด้วย `caffeinate -i` (กันแมคหลับ)

## (สำรอง) ทางรับข้อมูล UDP — ใช้เมื่อเดินสาย USB ถึงแมคไม่ได้

ESP32 ส่ง CSI ทาง WiFi มาที่แมค · แมคใช้เน็ตได้ผ่าน iPhone ทางสาย USB · serial ยังใช้ได้เป็นทางสำรอง

### Firmware ที่ต้องอยู่บนบอร์ด — ✅ flash แล้วทั้งคู่ (2026-11-11)

| บอร์ด | MAC | firmware | build จาก |
|---|---|---|---|
| **#1** active_ap | `...6a:b8` | UDP · คิว + task แยก · กรอง MAC #2 · unicast ผ่าน `HELLO` · บรรทัด `STAT` | `active_ap/build_udp` |
| **#2** active_sta | `...78:cc` | ส่ง 100 pkt/s จังหวะคงที่ · **ไม่วัด CSI ฝั่ง #2** | `active_sta/build_nocsi` |

**ทำไมต้องเป็น firmware ชุดนี้** — วัดจริงที่ตำแหน่งทดสอบ (ไม่ใช่ตำแหน่งเก็บ):

| | อัตรา (pkt/s) | ต่ำสุดรายวินาที | SD | ช่องขาด > 50 ms / 60 วิ |
|---|---:|---:|---:|---:|
| firmware เดิม (broadcast) | 42.2 | 0 | 35.5 | 245 |
| **firmware ใหม่ (unicast)** | **99.9** | **96** | **0.9** | **0** |

ต้นเหตุของเดิม: ตัวส่งของ #2 ไม่ได้คุมอัตราจริง (คำนวณ lag ผิด) และ #1 ส่ง UDP ใน WiFi callback
โดยไม่เช็คผล — broadcast ที่ 1 Mbps ส่งไม่ออก 73% แบบเงียบ ๆ · ชุดข้อมูลแรก 73 pkt/s ก็มาจากบั๊กนี้
รายละเอียด: `docs/reports/esp_build_worklog.md`

ถ้าต้อง flash ใหม่ (เช่นบอร์ดพัง) — **อย่าใช้ menuconfig และอย่าใช้โฟลเดอร์ `build/`**
(`build/` กับ `sdkconfig` ใน active_ap เป็นโหมด serial):

```bash
. ~/esp/esp-idf-v5.4/export.sh
cd fall_detection_backend/ESP32-CSI-Tool

# #1 — เช็ค MAC ก่อน ต้องเป็น ...6a:b8
esptool.py -p /dev/cu.usbserial-0001 read_mac
cd active_ap && idf.py -B build_udp -D SDKCONFIG=build_udp/sdkconfig \
    -D SDKCONFIG_DEFAULTS="sdkconfig.datacollect_udp.defaults" -p /dev/cu.usbserial-0001 build flash

# #2 — เช็ค MAC ก่อน ต้องเป็น ...78:cc
cd ../active_sta && idf.py -B build_nocsi -D SDKCONFIG=build_nocsi/sdkconfig \
    -D SDKCONFIG_DEFAULTS="sdkconfig.datacollect.keep;sdkconfig.datacollect_nocsi.defaults" \
    -p /dev/cu.usbserial-0001 build flash
```

⚠️ บอร์ดสองตัวใช้ชิป CH340 พอร์ตขึ้นชื่อ `usbserial-0001` เหมือนกัน **แยกด้วย MAC เท่านั้น** · แปะเทปเขียนเลขไว้
⚠️ **เปลี่ยนบอร์ด #2 = ต้องแก้ `CONFIG_CSI_UDP_SOURCE_MAC`** ใน `sdkconfig.datacollect_udp.defaults` แล้ว flash #1 ใหม่
ไม่งั้น #1 จะทิ้ง CSI ของ #2 ตัวใหม่ทั้งหมด (`STAT` ขึ้น `skip` สูง · `sent` ≈ 0)

### unicast ทำงานยังไง

collector ส่ง `HELLO` ไปที่ `192.168.4.1:5501` ทุก 2 วิ → #1 ส่ง CSI ตรงมาที่ IP ของแมค
(มี ACK + ส่งซ้ำ + ใช้ความเร็วสูง) · ถ้าเงียบเกิน 10 วิ #1 กลับเป็น broadcast เอง
ไม่ต้องตั้ง IP อะไร · `csi_collector_serial.py` และ `udp_rate_check.py` ส่ง `HELLO` ให้อัตโนมัติ

### เช็คอัตราก่อนเริ่ม — ทำที่ตำแหน่งเก็บจริง

```bash
python data_collection/udp_rate_check.py 60 site hello
```

| ค่า | ผ่าน |
|---|---|
| `rate` | ≈ 100 |
| `per_sec_min` | ≥ 90 |
| `per_sec_stdev` | < 3 |
| `gaps_over_50ms` | ≈ 0 |
| `at_#1_per_s` → `qdrop` / `fail` | 0 |
| `at_#1_dest` | `unicast` |

ไม่ผ่าน → ดู `at_#1_per_s`: `cb` ต่ำ = #2 ส่งไม่ถึง (ระยะ/ของกั้น) · `skip` สูง = MAC #2 ไม่ตรง ·
`fail`/`qdrop` สูง = #1 ส่งไม่ทัน (มีเครื่องอื่นแย่งช่อง) · `dest=broadcast` = HELLO ไม่ถึง #1
ผลทุกครั้งต่อท้ายใน `data/sessions/udp_rate_checks.jsonl`

### แมคเกาะ `myssid` ไม่ติด ขึ้น "Connection timeout"

เจอจริง 2026-11-11 · log ของ #1 ขึ้น `station: <mac> join` แล้ว `leave, reason = 15`
(4-way handshake timeout = รหัสไม่ตรง) ทั้งที่พิมพ์ `mypassword` ถูก — แมคใช้รหัสเก่าที่จำไว้

แก้: Wi-Fi → `myssid` → **Forget This Network** · Keychain Access → ค้น `myssid` → ลบทุกรายการ
แล้วเกาะด้วยคำสั่ง `networksetup -setairportnetwork en0 myssid mypassword`

> log ของ #1 ขึ้น `ESP32 STA joined AP` กับ**ทุก**เครื่องที่เกาะ ไม่ใช่เฉพาะ #2 — ดู MAC ประกอบ
> (#2 = `1c:c3:ab:b9:78:cc` · แมค/iPhone ใช้ MAC สุ่ม)

### ให้แมคใช้เน็ตได้ระหว่างเก็บ — iPhone ทางสาย USB

WiFi ของแมคต้องเกาะ `myssid` ไว้ จึงต้องเอาเน็ตจากอีกทางหนึ่ง:

1. iPhone: **ปิด Wi-Fi** แล้วเปิด **Personal Hotspot**
   (ปิด Wi-Fi ก่อน = แชร์ทางสาย/Bluetooth อย่างเดียว ไม่ปล่อยคลื่น 2.4GHz มากวน CSI)
2. เสียบสาย iPhone เข้าแมค → กด Trust ถ้าถาม
3. System Settings → Network → ⋯ → **Set Service Order** → ลาก **iPhone USB ขึ้นเหนือ Wi-Fi**
   ไม่งั้นแมคจะพยายามออกเน็ตผ่าน ESP32 (`192.168.4.1`) ซึ่งไม่มีเน็ต
4. แมคเกาะ WiFi `myssid`

เช็ค: `route -n get default | grep interface` ต้อง**ไม่ใช่** `en0` · เปิดเว็บได้ ·
`udp_rate_check.py` ผ่าน

⚠️ วาง iPhone ไว้ข้างแมค ห้ามหยิบขึ้นมาใช้ระหว่าง session · ห้ามเปิด Wi-Fi ของ iPhone
· ถ้า iPhone หลุด เน็ตหายอย่างเดียว การเก็บข้อมูลไม่สะดุด (UDP มาทาง WiFi)

⚠️ **วางคอมให้ห่างจากบริเวณที่ทำท่า และห้ามขยับตลอด session** — คอมที่เกาะ AP
กลายเป็นแหล่งสัญญาณเพิ่มบนช่องเดียวกัน ถ้าขยับคอมระหว่างเก็บจะปนเข้าไปในข้อมูล

## ⚠️ (เฉพาะโหมด UDP) ตั้งค่าแมคก่อนเก็บทุกครั้ง — เจอจริง 2026-11-11

ถ้าข้ามข้อไหน อัตราจะแกว่ง 30-190 pkt/s · #1 ส่งไม่ออก 100+/วิ · #2 ส่งซ้ำจนข้อมูลมีเฟรมซ้ำ

| ทำ | ทำไม |
|---|---|
| **เสียบสายชาร์จแมค + ปิด Low Power Mode** (Battery → Low Power Mode → Never) | **ต้นเหตุหลัก** — ใช้แบต + Low Power Mode ทำให้ WiFi แมคประหยัดไฟ #1 ต้องพักข้อมูลรอ คิวเต็ม |
| ปิด AirDrop (No One) + Handoff · ถ้า `ifconfig awdl0` ยัง UP → `sudo ifconfig awdl0 down` ใน Terminal | AWDL ทำให้วิทยุแมคกระโดดออกจากช่อง 6 เป็นระยะ |
| iPhone ปิด Wi-Fi (ใช้เน็ตทางสาย USB) | hotspot ทาง WiFi ปล่อยคลื่นในห้อง |
| ปิด Auto-Join ของ WiFi บ้าน | ทุกครั้งที่ #1 รีบูต แมคจะกระโดดกลับไป WiFi บ้านเอง |
| รันหน้าเว็บด้วย `caffeinate -i` (ดูคำสั่งข้างล่าง) | กันแมคหลับกลาง session |

เช็คที่ป้ายบนหน้าเว็บ: อัตรา 90-110 · `#1 unicast · คิวเต็ม 0 · ส่งพลาด 0 · ทิ้งซ้ำ ~0`
(firmware #1 ทิ้งเฟรมที่ #2 ส่งซ้ำให้แล้ว — ข้อมูลไม่ซ้ำแม้ช่องแน่น แต่ "ทิ้งซ้ำ" เยอะ = ช่องมีปัญหา)

## 📶 ทดสอบลิงก์ — ทำก่อนทุก session (แผง "ทดสอบลิงก์" ในหน้าเว็บ + ป้ายบนสุด)

อัตรา 100 pkt/s ครบไม่ได้แปลว่าข้อมูลดี — session 20261111_1333 อัตราครบทุกไฟล์ แต่ด่านนำร่องไม่ผ่าน
เพราะสัญญาณกระตุกจนกลบท่าคน · วัดสด 5 วิล่าสุด (ไม่ต้องเก็บไฟล์)

| ตัวเลข | วัดยังไง | ผ่าน | ชุดแรก (Data_2) | 13:33 (ไม่ผ่าน) |
|---|---|---|---:|---:|
| **กระตุก** | ทุกคนนิ่ง 10 วิ · แอมพลิจูดหาร gain แล้วเปลี่ยนเฉลี่ยกี่ % ต่อ packet | ≤ 5% | 3.8% | 9.0–9.3% |

| **การเคลื่อนไหว** | คนแสดงเดินไป-กลับผ่านจุดทำท่า 10 วิ เทียบตอนนิ่ง | ≥ 3 เท่า | — | — |

ไม่ผ่าน → แก้ทีละอย่าง ดูตัวเลขเปลี่ยนสด ๆ (ไม่ต้องรีสตาร์ทโปรแกรม):
1. **ปิด Wi-Fi ของแมค** — ใช้เน็ตจาก iPhone ทางสาย USB (iPhone ปิด Wi-Fi ด้วย) · แมคอยู่ห่าง #1 ไม่ถึงเมตร

   เพื่อนบ้านที่ช่อง 6 (40 MHz), 6, 10, 11 ซ้อนอยู่ในย่านนี้ (สแกนจากแมค 2026-11-11)
3. ย้ายจุดวาง / หมุนบอร์ดให้เสาอากาศ (ปลายบอร์ดที่มีลายทองคดไปมา) หันเข้าหากัน ไม่โดนกล่องบัง

### ⚠️ ทำไมต้องอุ่นบอร์ดก่อน 10-15 นาที

ในโหมด UDP ทุก CSI sample กลายเป็น packet WiFi ที่ต้องส่งออกอากาศ
(~750 ไบต์ × 100 ครั้ง/วินาที ≈ 75 KB/s ส่งไม่หยุด) กำลังส่งตั้งไว้สูงสุด 20 dBm
**ESP32 #1 จึงร้อนขึ้นชัดเจนที่ฝาเหล็กของโมดูล** — ตรวจแล้วว่าเป็นที่ชิป ไม่ใช่ที่ LDO
แปลว่าการจ่ายไฟปกติ ชิปทำงานหนักตามหน้าที่ ไม่ใช่ความผิดปกติ

**ปัญหาไม่ใช่ความร้อนเอง (ESP32 รับได้ถึง 85°C) แต่เป็นค่า CSI ที่ดริฟต์ตามอุณหภูมิ**
ถ้าเริ่มเก็บตอนบอร์ดเพิ่งเสียบไฟ ค่าที่วัดได้ช่วงต้น session จะต่างจากช่วงท้าย
= **คอนฟาวด์แบบเดียวกับที่ทำให้ dataset ชุดแรกใช้ไม่ได้** แค่เปลี่ยนจาก "สภาพห้อง"
เป็น "อุณหภูมิบอร์ด"

โหมด session สลับคลาสช่วยกันไว้อยู่แล้ว (ทั้งสองคลาสกระจายทั่วช่วงเวลาเท่ากัน
ดริฟต์จึงกระทบเท่ากัน ไม่ผูกกับคลาสใดคลาสหนึ่ง) **แต่อย่าพึ่งอย่างเดียว**
อุ่นบอร์ดให้อุณหภูมิเข้าที่ก่อนจะตัดตัวแปรนี้ออกไปเลย

> ทางเลือกที่ยังไม่ได้ทำ: ลดกำลังส่งเป็น 15 dBm ด้วย `esp_wifi_set_max_tx_power(60)`
> ใน `softap_init()` จะลดความร้อนลงมาก และ **ไม่กระทบคุณภาพ CSI** เพราะ CSI วัดจาก

> ตัดสินใจไว้ว่าใช้ฮีตซิงก์ + อุ่นบอร์ดก่อน ถ้ายังร้อนเกินไปค่อยมาลดกำลังส่ง

### หน้าที่สองคน

| | ทำอะไร |

⚠️ **คนกดต้องนั่งที่เดิม ท่าเดิม ตลอด session** — ตัวคนกดก็อยู่ในสนามสัญญาณเหมือนกัน
ถ้านั่งนิ่งที่เดิมตลอด จะกลายเป็นส่วนหนึ่งของห้องที่เท่ากันทุกท่า ไม่เป็นปัญหา

### วิธีกดแต่ละท่า — หน้าจอบอกทุกครั้งว่าต้องกดตอนไหน

| ท่า | แบบ | กด Enter ครั้งที่ 1 (มาร์ค) | ครั้งที่ 2 |
|---|---|---|---|
| 🔴 ล้ม 4 ท่า | มาร์ค | **ตัวถึงพื้น** | หยุด ~2 วิหลังมาร์ค |
| 🟢 ก้มเก็บของ | มาร์ค | **มือแตะของ** (จุดที่ก้มต่ำสุด) | หยุด ~2 วิหลังมาร์ค |
| 🟢 นอนลงบนพื้น | มาร์ค | **ตัวแนบพื้น** | หยุด ~2 วิหลังมาร์ค |
| 🟢 สะดุดแต่ไม่ล้ม | มาร์ค | **เท้าสะดุด** | หยุด ~2 วิหลังมาร์ค |
| 🟢 ยืนนิ่ง · เดิน | ต่อเนื่อง | — | หยุดที่ ~7 วิ (กดครั้งเดียว) |
| 🟢 ห้องว่าง | อัตโนมัติ | — | — (สคริปต์หยุดเอง) |

**ทำไม non_fall ต้องมาร์คด้วย** — `preprocess_v3` ตัด window รอบจุดมาร์คของทุกท่า
ทั้งสองคลาสจึงมาจากช่วงเดียวกันของคลิป (ก่อนหน้านี้ non_fall ตัดจาก 4 วิแรก
ถ้าก้มเก็บของช้ากว่านั้น ตัวท่าจะหลุดออกนอก window ทั้งหมด) · ท่าต่อเนื่องที่ไม่มี
จังหวะให้มาร์ค ระบบตัดที่ตำแหน่ง 5.5 วิ (547 pkt) ให้ตรงกับท่าที่มาร์ค

### จังหวะของท่าที่มาร์ค — เหมือนกันทั้ง fall และ non_fall

```
[ยืนปกติ ≥ 5 วินาที / จนได้ยินเสียงยาว]  →  ทำท่า  →  คนกด Enter/Space ตอนเกิดเหตุ
   →  [อยู่ท่านั้นต่ออีก 2 วิ]  →  คนกด Enter หยุด
```

- **ยืนอย่างน้อย 5 วินาทีก่อนทำท่า** — ต้องการ ≥ 342 packet (3.4 วิ) ก่อนจุดมาร์ค
  สคริปต์จะเตือนทันทีถ้าเร็วไป
- **หยุด 2 วิหลังมาร์ค ไม่ต้องรอนานกว่านั้น** — หน้าเว็บติ๊ง 2 ครั้งและปุ่มเปลี่ยนเป็นสีเขียว
  "หยุดได้แล้ว" ให้เอง · ขั้นต่ำคือ 0.7 วิ (ต่ำกว่านี้ระบบเตือน)
  ทำไมไม่รอนาน: framed ใช้ถึงมาร์ค +0.7 วิ · continuous ทิ้งท่าล้มหลังถึงพื้น +0.3 วิ
  (นอนนิ่งหลังล้ม แยกจาก "นอนลงบนพื้น" ไม่ได้) · ข้อมูลหลังจากนั้นไม่ถูกใช้ · รอเต็ม 12 วิแบบเดิม
  = นอนบนพื้นเปล่า ๆ ~7 วิ × 396 รอบ ≈ 40 นาที
- ท่าต่อเนื่อง (ยืนนิ่ง · เดิน) หน้าเว็บติ๊งที่ 7 วิ — หยุดได้เลย
- **อย่ากด Enter รัว** — ใช้ 2 ครั้งพอดี ครั้งที่ 3 จะไปตอบคำถาม "บันทึกไหม?"
  เป็นค่าว่าง แล้วสคริปต์จะทิ้ง sample นั้น (เก็บซ้ำได้ ไม่เสียหาย)
- ทิ้ง sample ไหน สคริปต์จะให้เก็บท่าเดิมซ้ำ **ทันทีในตาถัดไป** (ไม่ไปกองไว้ท้าย session)

### ท่า "ห้องว่าง" — ทั้งสองคนออกจากห้อง

```
คนกดกด Enter เริ่ม  →  ทั้งสองคนออกจากห้องภายใน 15 วิ  →  สคริปต์บันทึก 1230 pkt (~12 วิ)
   →  แมคส่งเสียงติ๊ง  →  กลับเข้ามา  →  ตอบ y
```

- สคริปต์เริ่มและหยุดเอง ไม่มีใครต้องอยู่ในห้องกด Enter — ช่วงที่บันทึกจึงไม่มีคนเดินปน
- ⚠️ **ประตูต้องอยู่สภาพเดียวกับตอนเก็บท่าอื่น** — ถ้าปกติเปิดไว้ ตอนออกก็ปล่อยเปิด
  ถ้าปิดประตูเฉพาะตอนเก็บห้องว่าง โมเดลจะเรียนว่า "ประตูปิด = ห้องว่าง" แทน
  (คอนฟาวด์แบบเดียวกับชุดข้อมูลแรก) · แนะนำเปิดประตูทิ้งไว้ทั้ง session
- ออกไปให้พ้นแนวประตู อย่ายืนรอตรงขอบประตู

### เช็คบนหน้าจอทุกครั้งที่เก็บท่ามาร์ค

```
รับมา 1215 pkts · 100 pkt/s   📍 มาร์คที่ pkt 540 (5.4 วิ)      ← ต้องเห็นบรรทัดนี้
```
ถ้าขึ้น `⚠️ ไม่มีจุดมาร์ค` · `⚠️ ทำท่าเร็วไป` · `⚠️ หยุดเร็วไป` · `⚠️ อัตราต่ำ` · `⚠️ ข้อมูลขาดช่วง` → ตอบ `n` ทิ้งแล้วเก็บใหม่
(`ข้อมูลขาดช่วง` เกิน 0.3 วิ = packet หายเป็นช่วงหรือ ESP32 รีบูต — อัตราเฉลี่ยอาจยังดูปกติ)
(`อัตราต่ำ` ซ้ำหลายตา = หยุด session แล้วรัน `udp_rate_check.py` หาสาเหตุ)
ท่าต่อเนื่องถ้าขึ้น `⚠️ สั้นไป` → ตอบ `n` เหมือนกัน

### ห้ามตลอด session

- ❌ reboot / ถอดปลั๊ก ESP32 (ถอดแล้วต้องอุ่นใหม่ 10-15 นาที)
- ❌ ขยับ ESP32 ทั้งสองตัว
- ❌ ย้ายเฟอร์นิเจอร์ / เปิด-ปิดประตูหน้าต่างเปลี่ยนไปจากเดิม
- ❌ มีคนอื่นเดินผ่าน
- ❌ คนกดลุกจากที่นั่ง / ย้ายที่นั่ง (ยกเว้นตอนออกจากห้องในท่า "ห้องว่าง")
- ❌ ขยับแมค / เปิด-ปิดฝาแมค

## 🚦 ด่านนำร่อง — ทำหลังคนแรกเก็บ ~30 รอบ ก่อนเก็บต่อ

**ทำไม:** `udp_rate_check` บอกได้แค่ว่าข้อมูลมาครบ ไม่ได้บอกว่าข้อมูล "เห็นคน" — ถ้าจุดทำท่าไม่อยู่ใน
แนวสัญญาณระหว่าง #1 กับ #2 ทุกไฟล์ดูปกติหมด แต่การล้มแทบไม่ทิ้งร่องรอย รู้อีกทีตอนเทรนหลังเก็บครบ
(รอบซ้อม 03:47 ไม่ได้ทำท่าจริง จึงยังไม่มีหลักฐานทั้งว่าเห็นหรือไม่เห็น) · ตัววัดการเคลื่อนไหวแบบง่าย
ที่ลองแล้วเชื่อถือไม่พอ (gain ของ ESP32 กระโดดเป็นขั้น) → ตัดสินด้วยโมเดลจริงบนข้อมูลจริง

**ทำ:** คนแรกเก็บ ~30 รอบ (ทำท่าจริง) แล้วจบ session → ปิดหน้าเว็บก็ได้ แล้วรัน

```bash
python experiments/pilot_check.py --actor 1
```

RandomForest แบ่ง test ตามไฟล์ (ไม่รวมห้องว่าง) เทียบกับสลับ label สุ่ม 20 ครั้ง · ลอง feature 2 แบบ
(preprocess ปัจจุบัน / subcarrier ที่ถูก + หาร gain ต่อ packet) · ผลต่อท้ายใน `data/sessions/pilot_checks.jsonl`

| ผล | แปลว่า |
|---|---|
| ✅ ผ่าน (balanced acc ≥ 70% และ p ≤ 0.05) | ตำแหน่งใช้ได้ เก็บต่อ |
| ✅ ผ่านเฉพาะแบบปรับปรุง | ตำแหน่งใช้ได้ · **ต้องแก้ preprocess_v3 ก่อนเทรน** |

| ❌ ไม่ผ่าน | **หยุด** — ย้าย ESP32 ให้จุดทำท่าอยู่กลางแนว #1↔#2 แล้วนำร่องใหม่ (ย้ายไฟล์ชุดนี้ไปเก็บแยก) |

ทดสอบสคริปต์แล้วกับข้อมูลจำลอง: ไม่มีสัญญาณ → ❌ (43-53% vs สุ่ม 46%) · มีสัญญาณ + gain กระโดด

60 ไฟล์ให้ความแม่น ±12% — พอบอกว่า "เห็น" หรือ "ไม่เห็น" ไม่พอใช้รายงานผล
