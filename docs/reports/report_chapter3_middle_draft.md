# บทที่ 3
# การวิเคราะห์และออกแบบระบบ

## ขั้นตอนในการดำเนินงาน

ระบบตรวจจับการล้มของผู้สูงอายุด้วย WiFi CSI และแอปพลิเคชันแจ้งเตือนผู้ดูแล มีขั้นตอนในการดำเนินงานโดยเริ่มจากการศึกษาปัญหาการหกล้มของผู้สูงอายุ ศึกษาเทคโนโลยี WiFi CSI และแนวทางการตรวจจับกิจกรรมมนุษย์ จากนั้นจึงวิเคราะห์ความต้องการของระบบ ออกแบบสถาปัตยกรรม พัฒนาอุปกรณ์และซอฟต์แวร์ ทดสอบการทำงาน และปรับปรุงระบบให้สามารถใช้งานแบบต้นแบบได้

ขั้นตอนการดำเนินงานของระบบมีดังต่อไปนี้

- ศึกษาปัญหาและรวบรวมข้อมูลเกี่ยวกับการหกล้มของผู้สูงอายุ ระบบตรวจจับการล้ม และเทคโนโลยี WiFi CSI
- วิเคราะห์ความต้องการของผู้ใช้งาน ได้แก่ ผู้สูงอายุ ผู้ดูแล และผู้ดูแลระบบ
- ออกแบบสถาปัตยกรรมระบบที่เชื่อมต่อระหว่าง ESP32, Backend API, ML Service, ฐานข้อมูล และแอปพลิเคชันผู้ดูแล
- ออกแบบและพัฒนาส่วนเก็บข้อมูล WiFi CSI ด้วย ESP32 และกระบวนการแปลงข้อมูลเป็นคุณลักษณะสำหรับโมเดล
- พัฒนา Machine Learning Service สำหรับจำแนกเหตุการณ์การล้มและเหตุการณ์ที่ไม่ใช่การล้ม
- พัฒนา Express API สำหรับรับข้อมูลจากอุปกรณ์ เรียกใช้ ML Service บันทึกเหตุการณ์ และจัดการการแจ้งเตือน
- พัฒนาแอปพลิเคชัน Middle สำหรับผู้ดูแล เพื่อรับแจ้งเตือน ดูเหตุการณ์ และกดยืนยันการรับทราบ
- ทดสอบระบบแบบ End-to-End ตั้งแต่การส่งข้อมูล การประมวลผล การบันทึกข้อมูล การแจ้งเตือน และการยืนยันรับทราบ
- ปรับปรุงระบบจากผลการทดสอบและจัดทำเอกสารประกอบโครงงาน

ภาพที่ 3.1 ขั้นตอนในการดำเนินงานของระบบ

## สถาปัตยกรรมระบบ

สถาปัตยกรรมของระบบแบ่งออกเป็น 5 ชั้นหลัก ได้แก่ ชั้นอุปกรณ์ตรวจจับ ชั้นรับและเตรียมข้อมูล ชั้นบริการประมวลผล ชั้นฐานข้อมูลและการแจ้งเตือน และชั้นแอปพลิเคชันผู้ดูแล โดยแต่ละส่วนทำงานร่วมกันเพื่อให้ระบบสามารถตรวจจับเหตุการณ์การล้มและแจ้งเตือนไปยังผู้ดูแลได้อย่างเป็นลำดับ

ชั้นอุปกรณ์ตรวจจับใช้ ESP32 จำนวน 2 ตัว ตัวหนึ่งทำหน้าที่สร้างเครือข่ายและรับข้อมูล CSI ส่วนอีกตัวทำหน้าที่ส่ง packet เพื่อให้ตัวรับสามารถวัดการเปลี่ยนแปลงของสัญญาณ WiFi ได้ ข้อมูล CSI ที่ได้จะถูกส่งผ่าน USB Serial เข้าสู่เครื่องคอมพิวเตอร์สำหรับจัดเก็บและเตรียมข้อมูลในระยะต้นแบบ

ชั้นบริการประมวลผลประกอบด้วย Express API และ FastAPI ML Service โดย Express API ทำหน้าที่เป็นศูนย์กลางรับ request จากอุปกรณ์หรือระบบทดสอบ ตรวจสอบ API key เรียกใช้งาน ML Service และจัดการเหตุการณ์ ส่วน ML Service ทำหน้าที่รับ feature vector และจำแนกว่าเหตุการณ์นั้นเป็นการล้มหรือไม่

ชั้นฐานข้อมูลและการแจ้งเตือนใช้ Supabase สำหรับจัดเก็บเหตุการณ์การล้มและ push token ของอุปกรณ์ผู้ดูแล ใช้ Expo Push Notification สำหรับส่งแจ้งเตือนแบบทันทีไปยังแอปพลิเคชัน Middle และใช้ Twilio Voice Call สำหรับยกระดับการแจ้งเตือนเมื่อไม่มีการตอบรับภายในเวลาที่กำหนด

## แผนผังระบบงาน

แผนผังระบบงานระดับ Context Diagram แสดงภาพรวมของระบบโดยกำหนดให้ระบบตรวจจับการล้มเป็นศูนย์กลาง และมีหน่วยงานภายนอกที่เกี่ยวข้อง ได้แก่ ผู้สูงอายุ ผู้ดูแล ผู้ดูแลระบบ Supabase Expo Push Notification และ Twilio ผู้สูงอายุเป็นแหล่งกำเนิดการเคลื่อนไหวในพื้นที่ตรวจจับโดยไม่ต้องกดใช้งานระบบโดยตรง ส่วนผู้ดูแลเป็นผู้รับแจ้งเตือน ดูรายละเอียดเหตุการณ์ และกดยืนยันการตรวจสอบผ่านแอปพลิเคชัน

ข้อมูลหลักที่ไหลเข้าสู่ระบบคือข้อมูล CSI หรือ feature จากอุปกรณ์ ESP32 เมื่อระบบตรวจพบการล้ม ข้อมูลเหตุการณ์จะถูกส่งไปยังฐานข้อมูลและบริการแจ้งเตือน ผู้ดูแลจะได้รับข้อความแจ้งเตือนผ่านแอปพลิเคชัน และสามารถส่งข้อมูลการยืนยันรับทราบกลับเข้าสู่ระบบได้ หากไม่มีการตอบรับ ระบบจะส่งคำสั่งไปยัง Twilio เพื่อโทรแจ้งเตือนเบอร์ฉุกเฉิน

## แผนผังเครือข่าย

การเชื่อมต่อเครือข่ายในระยะต้นแบบใช้ ESP32 จำนวน 2 ตัว ได้แก่ ESP32 ตัวรับสัญญาณ CSI และ ESP32 ตัวส่ง packet ตัวรับทำหน้าที่สร้างเครือข่าย WiFi สำหรับการวัด CSI และรับ packet จากตัวส่ง เมื่อมีการเคลื่อนไหวในพื้นที่ สัญญาณ WiFi ที่ตัวรับได้รับจะเปลี่ยนแปลงตามลักษณะของการเคลื่อนไหว ข้อมูล CSI จะถูกส่งออกจาก ESP32 ตัวรับผ่าน USB Serial ที่ความเร็ว 921600 baud ไปยังคอมพิวเตอร์สำหรับจัดเก็บข้อมูลและส่งต่อเข้าสู่ขั้นตอนประมวลผล

ในต้นแบบนี้การรับข้อมูล CSI ใช้ USB Serial เพื่อควบคุมสภาพแวดล้อมการเก็บข้อมูล ลดปัญหาจากเครือข่ายภายนอก และทำให้ตรวจสอบข้อมูลได้ง่าย ส่วนแนวทางสำหรับการพัฒนาต่อสามารถปรับให้ ESP32 ส่งข้อมูลขึ้น Backend API โดยตรงผ่านเครือข่าย WiFi และเพิ่มการตั้งค่า WiFi ผ่านแอปพลิเคชันในอนาคต

ภาพที่ 3.5 แผนผังเครือข่ายของระบบตรวจจับการล้มด้วย ESP32 WiFi CSI

## การออกแบบโมเดลตรวจจับการล้ม

โมเดลตรวจจับการล้มของระบบต้นแบบใช้แนวทาง Machine Learning สำหรับจำแนกเหตุการณ์เป็น 2 ประเภท ได้แก่ fall และ no_fall ข้อมูลนำเข้าของโมเดลเป็น feature vector จำนวน 416 ค่า ซึ่งคำนวณจากข้อมูล CSI จำนวน 52 subcarriers และค่าสถิติจำนวน 8 ค่าในแต่ละ subcarrier ข้อมูลจะถูกปรับสเกลด้วย scaler ก่อนเข้าสู่โมเดล เพื่อให้ค่าคุณลักษณะอยู่ในช่วงที่เหมาะสมต่อการประมวลผล

โมเดลที่ใช้งานในระบบปัจจุบันคือ Random Forest โดย ML Service โหลดโมเดลจากไฟล์ `rf_v1.pkl` และโหลด scaler จากไฟล์ `scaler_rf_v1.pkl` เมื่อได้รับข้อมูล features ระบบจะเลือก window ล่าสุด นำข้อมูลไป normalize และให้โมเดลประเมินความน่าจะเป็นของการล้ม จากนั้นใช้ค่า threshold เท่ากับ 0.55 ในการตัดสินว่าเหตุการณ์นั้นเป็นการล้มหรือไม่ ผลลัพธ์ที่ส่งกลับไปยัง Backend API ประกอบด้วย prediction, confidence และ is_fall

## Data Pipeline

Data Pipeline ของระบบเริ่มจาก ESP32 ตัวส่ง packet ส่งสัญญาณไปยัง ESP32 ตัวรับ จากนั้นตัวรับอ่านค่า WiFi CSI และส่งข้อมูลออกผ่าน USB Serial ข้อมูลดิบถูกจัดเก็บในรูปแบบ CSV เพื่อใช้สำหรับการทดลองและการเตรียมข้อมูล ขั้นตอน preprocessing จะทำหน้าที่แยกข้อมูล CSI คำนวณค่าคุณลักษณะจาก subcarrier และสร้าง feature vector สำหรับใช้กับโมเดล Machine Learning

เมื่อระบบทำงานในโหมดตรวจจับ เหตุการณ์หรือ feature ที่ได้จะถูกส่งไปยัง Express API จากนั้น Express API เรียกใช้งาน ML Service ผ่าน endpoint `/predict` หากผลลัพธ์เป็น no_fall ระบบจะตอบกลับว่าอยู่ในสถานะ monitoring และไม่บันทึกเหตุการณ์ลงฐานข้อมูล แต่ถ้าผลลัพธ์เป็น fall ระบบจะบันทึกข้อมูลลงตาราง `fall_events` และเริ่มกระบวนการแจ้งเตือนผู้ดูแล

## Sequence Diagram การแจ้งเตือน

ลำดับการแจ้งเตือนเริ่มจากอุปกรณ์ส่งข้อมูล features ไปยัง Express API จากนั้น Express API เรียก ML Service เพื่อประมวลผล หากระบบตรวจไม่พบการล้มจะส่งผลลัพธ์กลับและจบขั้นตอน แต่หากตรวจพบการล้ม Express API จะตรวจสอบ cooldown ของอุปกรณ์ บันทึกเหตุการณ์ลง Supabase เริ่มจับเวลารอการตอบรับ และส่ง Push Notification ไปยังแอปพลิเคชัน Middle

เมื่อผู้ดูแลได้รับการแจ้งเตือน สามารถกดยืนยันการตรวจสอบได้ผ่านแอปพลิเคชัน ระบบจะเรียก endpoint `POST /api/v1/alert/ack/:event_id` เพื่อบันทึกการรับทราบและยกเลิก timer การยกระดับการแจ้งเตือน แต่หากไม่มีการตอบรับภายในเวลาที่กำหนด ระบบจะเรียก Twilio Voice Call เพื่อโทรแจ้งเตือน และบันทึกสถานะ escalated ลงฐานข้อมูล

## โครงสร้างฐานข้อมูล

ฐานข้อมูลของระบบในระยะต้นแบบใช้ Supabase โดยมีตารางหลัก 2 ตาราง ได้แก่ `fall_events` และ `push_tokens` ตาราง `fall_events` ใช้เก็บเหตุการณ์การล้มและสถานะการตอบรับ ส่วนตาราง `push_tokens` ใช้เก็บ token ของอุปกรณ์ผู้ดูแลสำหรับส่ง Push Notification ทั้งสองตารางเชื่อมโยงกันผ่านข้อมูล device_id ในเชิงการใช้งาน แม้ใน schema ปัจจุบันยังไม่ได้กำหนด foreign key โดยตรง

## การออกแบบส่วนติดต่อผู้ใช้

แอปพลิเคชัน Middle ออกแบบสำหรับผู้ดูแลเป็นหลัก โดยเน้นให้ผู้ใช้เห็นการแจ้งเตือนที่สำคัญได้รวดเร็ว มีหน้าหลักสำหรับแสดงรายการเหตุการณ์ มีการแยกสถานะเหตุการณ์ เช่น กำลังรอการตอบรับ รับทราบแล้ว และไม่มีการตอบรับ รวมถึงมีหน้าสำหรับจัดการบ้าน อุปกรณ์ และรายชื่อผู้ติดต่อฉุกเฉิน
