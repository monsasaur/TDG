## 1. ปัญหาและขอบเขต

ตอนนี้เวลาไม่มีใครกด acknowledge ระบบจะโทรออกด้วยข้อความ TTS **ตายตัวบรรทัดเดียว**
(`alertService.js:116`) ทุกเคสเหมือนกันหมด — ไม่บอกว่าล้มที่ไหน ไม่บอกว่านานแค่ไหนแล้ว
ไม่ต่างกันระหว่างตอนตี 3 กับตอนบ่าย

**Phase 2a ทำแค่:** ให้ Claude ร่างบทพูดภาษาไทยตามบริบทของเหตุการณ์นั้น ๆ แล้วส่งเข้า
Twilio TTS ตัวเดิม

### ✅ อยู่ในขอบเขต
- Service ใหม่ที่เรียก Claude ร่างบทพูด
- Fallback กลับไปข้อความเดิมเมื่อ AI ช้า/ล่ม/ปฏิเสธ
- บันทึกว่าสายนั้นใช้ AI หรือ fallback

### ❌ ไม่อยู่ในขอบเขต (อย่าทำ)
- **ห้ามแตะ trigger logic** — `escalationService.schedule/cancel/recoverPending` และ timer
  ทั้งหมดต้องเหมือนเดิมเป๊ะ AI ไม่มีสิทธิ์ตัดสินใจว่าเมื่อไหร่ควร escalate
- ไม่แตะ SMS (`alertService.sendSms`) — Phase 2a ทำเฉพาะการโทร
- ไม่ทำบทสนทนาสองทาง (`<Gather>`, speech-to-text webhook) — นั่นคือ Phase ถัดไป
- ไม่ต้องหา TTS provider ใหม่ (ดูข้อ 6.2)

## 2. Flow

```
escalate()  [ไม่แตะ — rule-based เหมือนเดิม]
   ├─ sendSms()                              [ไม่แตะ]
   └─ makeCall():
        ├─ aiVoiceAgentService.draftMessage(event)
        │     ├─ สำเร็จภายใน timeout → ได้บทพูดที่ปรับตามบริบท
        │     └─ ช้า / error / refusal / ข้อความไม่ผ่าน validation
        │              ↓
        └─────────► ใช้ข้อความคงที่เดิม  ← ทุกเส้นทางที่ไม่สำเร็จมาลงที่นี่
                    แล้วส่งเข้า Twilio <Say> ตัวเดิมทั้งคู่
```

**หลักการเดียวที่ห้ามละเมิด:** ไม่ว่าอะไรจะพัง ผู้ดูแลต้องได้รับสายเสมอ
AI เป็นแค่ตัวปรับปรุงเนื้อหา ไม่ใช่ตัวกลางที่ขวางทางได้

## 4. Interface ของ service ใหม่

`src/services/aiVoiceAgentService.js`

```js
/**
 * draftMessage — ร่างบทพูดภาษาไทยสำหรับสายฉุกเฉิน
 *
 * ห้าม throw ไม่ว่ากรณีใด — คืน null แล้วให้ผู้เรียกใช้ข้อความเดิมแทน
 * ความล้มเหลวของ AI ต้องไม่กลายเป็นความล้มเหลวของการโทร
 *
 * @returns {Promise<string|null>}  ข้อความไทยพร้อมอ่าน หรือ null เมื่อใช้ไม่ได้

draftMessage({ device_id, location, confidence, created_at, event_id })

/** เปิด/ปิดฟีเจอร์ทั้งก้อนจาก env */
```

**สัญญาที่ต้องรักษา**
1. ห้าม throw — ทุก error จับในตัวเอง คืน `null`

3. คืน `null` ถ้าฟีเจอร์ปิดอยู่ / ไม่มี API key
4. เขียน log ทุกครั้งว่าใช้ AI หรือ fallback พร้อมเหตุผลและเวลาที่ใช้

## 6. คำตอบของคำถามเปิด 5 ข้อในเอกสารออกแบบ

### 6.1 Latency — ตอบแล้ว: 3 วินาที

Twilio รับ TwiML ตอนสร้างสาย ไม่ได้รอระหว่างสายดัง เวลาที่ใช้ร่างบทพูดจึงบวกเข้ากับ
**เวลาก่อนเริ่มโทร** ตรง ๆ

ระบบรอ ack อยู่ 60 วินาทีแล้ว การเพิ่มอีก 3 วินาทีคิดเป็น 5% ยอมรับได้
เกินกว่านี้ให้ตัดไปใช้ข้อความเดิมทันที

**สำคัญ:** ยิง SMS กับร่างบทพูด**ขนานกัน** (`Promise.all` ที่ `escalationService.js:98`
ทำอยู่แล้ว) SMS จะได้ไม่ต้องรอ AI

### 6.2 Thai TTS — ตอบแล้ว: ไม่ต้องหา provider ใหม่เลย

ระบบใช้ `<Say language="th-TH" voice="Google.th-TH-Chirp3-HD-Kore">` ของ Twilio
อยู่แล้ว (`alertService.js:147`) เป็นเสียงไทยคุณภาพดี

**Phase 2a เปลี่ยนแค่ "ข้อความที่ป้อนเข้าไป" ไม่เปลี่ยนตัวอ่าน** — ตัดงาน integrate
TTS provider ใหม่ ตัดค่าใช้จ่าย ตัดความเสี่ยงออกทั้งก้อน

ข้อจำกัดที่ตามมาคือ **ข้อความต้องอ่านออกเสียงได้ดี** ดูกฎในข้อ 7

### 6.3 ต้นทุน — ตอบแล้ว: ประมาณ 0.02 บาทต่อสาย

| รายการ | จำนวน |
|---|---|
| Input (system prompt ~500 + event ~100) | ~600 token |
| Output (บทพูด ~320 ตัวอักษร) | ~150 token |
| ราคา Claude Opus 5 | $5 / 1M input · $25 / 1M output |
| **ต่อสาย** | ~$0.0068 ≈ **0.23 บาท** |
| **มี prompt caching** (system prompt คงที่) | input เหลือ ~10% → ≈ **0.15 บาท** |

เทียบกับค่าโทร Twilio ต่อสายแล้วแทบไม่มีนัยสำคัญ · ที่ 100 สาย/เดือน = ~15 บาท/เดือน

> ถ้าวัดแล้วยังไม่ทันภายใน 3 วินาที ให้ลอง `claude-haiku-4-5`
> ($1/$5 ต่อ 1M · 200K context) — งานนี้เป็นการเรียบเรียงข้อความสั้น
> ไม่ได้ต้องการการให้เหตุผลซับซ้อน **ตัดสินจากผลวัดจริง ไม่ใช่เดา**

### 6.4 การทดสอบ — ดูข้อ 9

### 6.5 Privacy — ตอบแล้ว: ส่งเฉพาะที่จำเป็น

**ส่งได้:** `location` (ชื่อห้อง), `confidence`, เวลาที่เกิดเหตุ, `device_id`

**ห้ามส่งเด็ดขาด:** ชื่อ-นามสกุลผู้สูงอายุ · เบอร์โทรผู้ดูแล · ที่อยู่ · ข้อมูลสุขภาพ ·
`event_id` แบบเต็ม (ใช้ 8 ตัวแรกพอถ้าต้องอ้างอิง)

ให้เขียนเป็น allowlist ในโค้ด **ไม่ใช่ blocklist** — สร้าง object ใหม่ที่มีเฉพาะ field
ที่อนุญาต อย่าส่ง `event` ทั้งก้อนเข้า prompt เพราะพอ schema เพิ่ม field ใหม่วันหลัง
มันจะหลุดไปเองโดยไม่มีใครรู้

ระบุใน `docs/` ว่าโครงการส่งข้อมูลอะไรออกไปที่ไหน — จำเป็นตอนทำเอกสาร PDPA

## 7. Prompt

**System prompt** (คงที่ ใส่ `cache_control` ไว้ให้ cache ได้)

```
คุณกำลังร่างข้อความสำหรับระบบโทรแจ้งเหตุฉุกเฉินอัตโนมัติ
ระบบตรวจพบว่าผู้สูงอายุอาจล้ม และไม่มีผู้ดูแลคนใดกดรับทราบในแอปภายในเวลาที่กำหนด
ข้อความที่คุณเขียนจะถูกอ่านออกเสียงให้ผู้ดูแลฟังทางโทรศัพท์

กฎ:
- ภาษาไทย สุภาพ กระชับ น้ำเสียงเร่งด่วนแต่ไม่ทำให้ตื่นตระหนก
- ไม่เกิน 2 ประโยค ความยาวรวมไม่เกิน 320 ตัวอักษร
- ต้องบอกให้ครบ: เกิดอะไร · ที่ไหน · นานแค่ไหนแล้ว · ให้ทำอะไรต่อ
- เขียนตัวเลขเป็นคำอ่าน ("สิบห้านาที" ไม่ใช่ "15 นาที")
- ห้ามใส่อีโมจิ ตัวย่อ วงเล็บ เครื่องหมายพิเศษ หรือคำภาษาอังกฤษ
- ห้ามวินิจฉัยอาการบาดเจ็บ ห้ามให้คำแนะนำทางการแพทย์
- ห้ามรับปากแทนใครว่าจะมีคนไปถึงเมื่อไหร่
```

**User message** — ส่งเฉพาะ field ที่อนุญาตตามข้อ 6.5

**พารามิเตอร์ที่ต้องใช้**

```js
{
  model: process.env.AI_VOICE_MODEL || 'claude-opus-5',
  max_tokens: 512,
  output_config: { effort: 'low' },   // งานสั้น ตรงไปตรงมา — ลด latency
  system: [{ type: 'text', text: SYSTEM_PROMPT, cache_control: { type: 'ephemeral' } }],
  messages: [{ role: 'user', content: eventSummary }]
}
```

- `effort: 'low'` — งานนี้คือเรียบเรียงข้อความ ไม่ต้องคิดหนัก ประหยัดทั้งเวลาและเงิน
- `cache_control` บน system prompt — system prompt ไม่เปลี่ยน ทำให้ input ถูกลง ~90%
- ใช้ `client.messages.create()` ธรรมดา ไม่ต้อง streaming (output สั้น)
- SDK: `@anthropic-ai/sdk` (npm)

## 8. Validation ก่อนใช้ข้อความ

**ห้ามเชื่อ output ตรง ๆ** ต้องผ่านทุกข้อ ไม่ผ่านข้อใดข้อหนึ่ง → ใช้ข้อความเดิม

| # | เช็ค | เหตุผล |
|---|---|---|
| 1 | `stop_reason !== 'refusal'` | โมเดลปฏิเสธ ต้องไม่เอา content ไปใช้ |
| 2 | ความยาว 1–`AI_VOICE_MAX_CHARS` ตัวอักษร | สั้นไปไม่มีข้อมูล ยาวไปสายลากยาว |
| 3 | มีอักษรไทยอย่างน้อย 60% | กันตอบเป็นอังกฤษหรือหลุด format |
| 4 | ไม่มี `<` `>` `&` | **สำคัญ** — ข้อความไปอยู่ใน TwiML ต้อง escape XML ก่อนเสมอ |
| 5 | ไม่มี URL / เบอร์โทร / อีโมจิ | อ่านออกเสียงไม่ได้ |

ข้อ 4 เป็นเรื่องความปลอดภัย ไม่ใช่แค่ความสวยงาม — ข้อความที่มี `<` จะทำให้ TwiML
พังทั้งก้อนและสายไม่ออกเลย **ต้อง escape ก่อนใส่ template ทุกกรณี รวมข้อความเดิมด้วย**

**สิ่งที่ทำให้งานนี้ไม่เหมือนงาน integrate AI ทั่วไป** คือมันอยู่บนเส้นทางที่คนอาจ
บาดเจ็บถ้าพัง เวลาเจอทางเลือกออกแบบ ให้เลือกทางที่ปลอดภัยกว่าเสมอแม้จะฉลาดน้อยกว่า

ถ้าเจอจุดที่ต้องเลือกระหว่าง "AI ตอบดีขึ้น" กับ "โทรออกได้แน่นอน" — เลือกอย่างหลังทุกครั้ง
โดยไม่ต้องถาม

Phase 2b (ให้ AI ช่วยตัดสินใจว่าเมื่อไหร่ควร escalate) **ยังไม่อนุญาต** ต้องผ่าน shadow mode
ตามเงื่อนไขใน [`hybrid_ai_escalation_design.md`](hybrid_ai_escalation_design.md) ก่อน
ถ้าระหว่างทำเห็นว่า "ตรงนี้ให้ AI ตัดสินใจน่าจะดีกว่า" — จดไว้ อย่าเพิ่งทำ
