# ผลการประเมินโมเดลใหม่ — แก้ปัญหาข้อมูลรั่ว

**วันที่:** 2026-09-01
**โค้ด:** `fall_detection_backend/ml_service/experiments/`
**ข้อมูล:** `data/processed_v2` — 2,412 window · 804 ไฟล์บันทึก · 3 window ต่อไฟล์

---

> **อ่านคู่กับ [`data_quality_audit_2026-09.md`](data_quality_audit_2026-09.md)**
> การตรวจข้อมูลหลังจากนี้พบว่า 95.6% ในเอกสารนี้มาจากการแยก session ที่บันทึก ไม่ใช่การจับการล้ม
> ตัวเลขทุกตัวในเอกสารนี้จึงเป็นการเทียบโมเดลบนฐานเดียวกัน ไม่ใช่ความสามารถจริงของระบบ

## สรุปสั้น

1. **ตัวเลข 97.9% ที่รายงานอยู่ วัดด้วยวิธีที่ข้อมูลรั่ว** — ตัวเลขที่ honest กว่าคือ **95.6% (fall recall 96.6%)**
2. **LSTM ไม่จำเป็น** — RandomForest ที่ดู window เดียวให้ผลดีกว่า LSTM ทุกแบบที่ข้อมูลรองรับ
3. **One-class ไม่เวิร์คกับ feature ชุดนี้** — ROC-AUC 0.70 เทียบกับ supervised 0.985 ตอบคำถาม mentor ได้แล้ว
4. **Threshold ที่เหมาะคือ 0.36 ไม่ใช่ 0.5** — ได้ fall recall เพิ่มจาก 96.6% เป็น 97.6%

## 1. ปัญหาที่พบในวิธีเทรนเดิม

### 1.1 ทุก sequence ประกอบจากคนละไฟล์ — วัดได้ 100%

```
แต่ละไฟล์บันทึกมี 3 window        (804 ไฟล์ × 3 = 2,412 window)
train_v3 ตั้ง SEQUENCE_LEN = 10   ← ต้องการ 10 window ติดกัน
→ ไฟล์เดียวไม่มีทางให้ 10 window ได้

วัดจริง: 2,394 sequence ที่ใช้เทรน คาบเกี่ยวมากกว่า 1 ไฟล์ทั้งหมด (100.0%)
```

`build_sequences()` ใน `train_v3.ipynb` เลื่อนหน้าต่างไปบน `X` ทั้งก้อนที่ต่อไฟล์เรียงกันไว้
โดยเช็คแค่ว่า label เหมือนกัน ไม่ได้เช็คว่ามาจากไฟล์เดียวกัน — sequence หนึ่งตัวจึงเป็น
window จากการล้มคนละครั้ง ~4 ครั้งเอามาต่อกัน **มิติเวลาที่ LSTM เรียนรู้คือลำดับที่สคริปต์
บังเอิญอ่านไฟล์ ไม่ใช่เวลาจริง**

### 1.2 ฝั่ง serving รู้ปัญหานี้แล้วและ workaround ไว้

`ml_service/app/preprocess.py`
```python
def get_features(self) -> list:
    """ใช้ window ล่าสุดอันเดียว ซ้ำ sequence_len ครั้ง
    เพราะ training sequences มาจากข้ามไฟล์ (แต่ละ window เป็นอิสระ)"""
    return [feat] * self.sequence_len
```

ตอนเทรนป้อน 10 window ที่ต่างกัน ตอนใช้งานป้อน window เดียวซ้ำ 10 ครั้ง —
**input คนละแบบกัน** และ LSTM layer ไม่ได้ทำงานอะไรเลยตอน inference

### 1.3 แบ่ง train/test แบบสุ่ม ไม่สนไฟล์

`train_v3.ipynb` ใช้ `train_test_split` ธรรมดา ทั้งที่ `preprocess_v2.py` เซฟ `file_ids.npy`
ไว้ให้แล้วแต่ไม่เคยถูกโหลด window ที่ซ้อนกัน 75% (window 200 / stride 50) จากการล้มครั้งเดียวกัน
จึงกระจายไปอยู่ทั้งสองฝั่ง

## 2. วิธีวัดใหม่

`experiments/eval_harness.py` บังคับ **StratifiedGroupKFold 5-fold แบ่งตามไฟล์บันทึก** —
ไฟล์เดียวกันอยู่ฝั่งเดียวเสมอ และสร้าง sequence ภายในไฟล์เดียวเท่านั้น
ทุกการทดลองใช้ฐานเดียวกันหมดเพื่อให้เทียบกันได้จริง

## 3. ผลเทียบสถาปัตยกรรม

`python experiments/run_baselines.py`

| โมเดล | Accuracy | Fall recall | ROC-AUC |
|---|---|---|---|
| **RandomForest (per-window)** | **95.6% ±0.5** | **96.6% ±0.9** | **0.985** |
| MLP (256,128) per-window | 94.9% ±1.0 | 95.7% ±0.4 | 0.985 |
| LSTM seq_len=2 | 94.6% ±1.8 | 94.3% ±2.0 | 0.984 |
| LSTM seq_len=3 | 94.4% ±1.0 | 93.2% ±2.2 | 0.980 |
| LogisticRegression | 92.5% ±1.6 | 93.7% ±1.5 | 0.973 |
| SVM (RBF) | 91.3% ±1.1 | 95.4% ±2.5 | 0.975 |
| *อ้างอิง: RandomForest + random split (รั่ว)* | *97.0% ±0.2* | *97.4% ±1.3* | *0.995* |

**ข้อสรุป**

- **LSTM ไม่ได้ช่วยอะไร** — แพ้ RandomForest ที่ดู window เดียวทั้ง accuracy และ fall recall
  สมเหตุสมผล เพราะข้อมูลไม่มีมิติเวลาให้เรียนตั้งแต่แรก (3 window ต่อไฟล์) และตอน serving
  ก็ยุบเหลือ window เดียวอยู่แล้ว
- **การรั่วทำให้ตัวเลขสูงขึ้นราว 1.4 จุด** (95.6% → 97.0%) และ ROC-AUC 0.985 → 0.995
  ไม่ถึงกับพลิกข้อสรุป แต่ตัวเลขที่รายงานต่อ mentor/ในรายงานควรใช้ตัวที่ไม่รั่ว
- ตัวเลข 97.9% เดิมเทียบตรง ๆ กับตารางนี้ไม่ได้ เพราะวัดคนละหน่วย (sequence vs window)

## 4. One-class — ตอบคำถาม mentor

`python experiments/run_oneclass.py` · เทรนด้วย non_fall 1,212 window เท่านั้น

| Detector | Accuracy | Fall recall | ROC-AUC |
|---|---|---|---|
| LocalOutlierFactor | 56.5% | 20.9% | 0.700 |
| OneClassSVM (rbf) | 57.4% | 23.8% | 0.684 |
| EllipticEnvelope | 50.8% | 11.5% | 0.526 |
| IsolationForest | 48.8% | 6.2% | 0.495 |

**ข้อสรุป: one-class ใช้แทน supervised ไม่ได้กับ feature ชุดนี้**

ROC-AUC ดีที่สุด 0.700 เทียบกับ supervised 0.985 — **ไม่ใช่แค่ปัญหา threshold**
ถ้าเป็นเรื่อง threshold อย่างเดียว AUC จะยังสูงแล้วแค่เลื่อนจุดตัด แต่ 0.70 แปลว่า
การล้มกับการเคลื่อนไหวปกติแยกกันไม่ค่อยออกในพื้นที่ feature นี้ ตราบใดที่ไม่เห็นตัวอย่างการล้ม

IsolationForest ที่ AUC 0.495 คือเดาสุ่ม — feature 416 มิติจากสถิติ 8 ตัว × 52 subcarrier
กระจายตัวไม่เหมาะกับการหา outlier แบบนี้

**ข้อดีที่คาดหวังไว้ยังจริงอยู่** (ไม่ต้องเก็บตัวอย่างครบทุกท่าล้ม) แต่ต้องเปลี่ยน
representation ก่อน เช่นใช้ autoencoder เรียน embedding แทนสถิติดิบ — ยังไม่ได้ลอง

## 5. Threshold tuning

`python experiments/run_threshold.py` · RandomForest out-of-fold ทั้ง 2,412 window

| threshold | fall recall | false alarm rate | ล้มที่พลาด | เตือนผิด |
|---|---|---|---|---|
| 0.30 | 97.9% | 12.3% | 25 | 149 |
| **0.36 (แนะนำ)** | **97.6%** | **9.6%** | **29** | **~118** |
| 0.40 | 97.2% | 8.3% | 33 | 100 |
| 0.50 (ค่าที่ใช้อยู่) | 96.6% | 5.4% | 41 | 65 |
| 0.70 | 89.0% | 2.9% | 132 | 35 |

**เกณฑ์ที่ใช้เลือก: ดัน fall recall ให้สูงสุดโดยคุม false alarm ≤ 10%**

เหตุผลที่ยอมให้เตือนผิดมากขึ้น — ระบบมี acknowledge flow อยู่แล้ว เตือนผิดผู้ดูแลกดปิดได้
ใน 60 วินาที ไม่มีใครโดนโทรฉุกเฉิน แต่การล้มที่พลาดคือไม่มีใครรู้เลย
ขยับจาก 0.5 → 0.36 แลกเตือนผิดเพิ่ม ~53 ครั้ง (จาก 2,412 window) กับล้มที่จับได้เพิ่ม 12 ครั้ง

## ⚠️ นี่ยังไม่ใช่ unseen test จริง

grouped split แก้ได้แค่**การรั่วระหว่าง window ในไฟล์เดียวกัน** แต่ทุกไฟล์ยังมาจาก
ชุดการเก็บข้อมูลเดิม — สภาพแวดล้อมเดียว ตำแหน่ง ESP32 เดิม คนเดิม

ตัวเลข 95.6% จึงยังตอบไม่ได้ว่าระบบทำงานได้แค่ไหนใน**บ้านที่ไม่เคยเห็น** ซึ่งเป็นสิ่งที่
mentor ขอจริง ๆ อันนั้นต้องเก็บข้อมูลใหม่ — คนละวัน คนละตำแหน่ง คนละคน
แล้วใช้เป็น test set ที่ไม่แตะตอนเทรนเลย

**จนกว่าจะมีชุดนั้น 95.6% / fall recall 96.6% คือตัวเลขที่ควรใช้รายงาน**

## สิ่งที่ควรทำต่อ

| ลำดับ | งาน | หมายเหตุ |

| 1 | เก็บ unseen test set | คนละวัน/ตำแหน่ง/คน — ต้องทำกับ ESP32 จริง |
