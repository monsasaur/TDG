# ต้องตัดสินใจ — CSI จะขึ้น cloud ได้ยังไงในบ้านลูกค้า

**สถานะ:** ยังไม่มีใครตัดสินใจ · **ขวางไม่ให้ระบบติดตั้งในบ้านจริงได้**
**วันที่:** 2026-09-02

---

## สรุปสั้น

ตอนนี้ระบบทำงานได้เฉพาะเมื่อ**มีคอมพิวเตอร์เปิดอยู่ในบ้าน** ซึ่งใช้เป็นสินค้าไม่ได้

ผมวัดตัวเลขจริงจากไฟล์ข้อมูลที่เก็บไว้แล้ว ข้อสรุปชัดมาก:

| ทางเลือก | Bandwidth ต่อบ้านต่อเดือน | ทำได้ไหม |
|---|---|---|
| ส่ง raw CSI ขึ้น cloud | **123 GB** (บีบเป็น binary แล้วยังเหลือ 67 GB) | ❌ ไม่ไหว |
| ESP32 คำนวณ feature แล้วส่ง | 18.7 GB | ⚠️ ยังเยอะ |
| **ESP32 คำนวณ + ส่งเฉพาะตอนมีการเคลื่อนไหว** | **~0.9–1.9 GB** | ✅ **แนะนำ** |

---

## 1. ปัญหา

### สิ่งที่มีตอนนี้

```
โหมดเก็บข้อมูล   ESP32 ──USB Serial──► Mac ──► ไฟล์ CSV      (ใช้ train)
โหมดทดลอง       ESP32 ──UDP:5500───► Mac ──► ML Service:8000  (csi_streamer.py)
```

### ทำไมใช้ในบ้านลูกค้าไม่ได้

**1. ทั้งสองทางต้องมีคอมพิวเตอร์อยู่ในบ้าน** — `csi_streamer.py` รันบนคอม ไม่ได้รันบน ESP32
ไม่มีลูกค้าคนไหนเปิด Mac ทิ้งไว้ 24 ชั่วโมงเพื่อให้เซนเซอร์ทำงาน

**2. `csi_streamer.py` ยิงตรงไป ML Service ข้าม Express API**
→ **ไม่บันทึก event · ไม่สร้าง alert · ไม่ยิง push · ไม่มี escalation**
flow แจ้งเตือนทั้งหมดที่สร้างไว้ไม่ทำงานเลยในเส้นทางนี้

**3. `ESP32-CSI-Tool` ไม่มีโค้ด HTTP client สักบรรทัด**
`csi_component.h` ส่งออกได้แค่ USB serial (`outprintf`) กับ UDP (`sendto`)

### คำถามที่ต้องตอบ

> **ใครคำนวณ 416 features ในบ้านลูกค้า และส่งขึ้น cloud ยังไง**

ตอน train เราใช้ `preprocess_v2.py` บนคอมคำนวณจากไฟล์ CSV — ในบ้านจริงไม่มีขั้นตอนนั้น

## 2. ตัวเลขที่วัดจริง

วัดจากไฟล์ใน `data/raw/Data_2.zip` ไม่ได้ประมาณเอา

```
1 บรรทัด CSI จริง = 511 ตัวอักษร  (128 ค่า = 52 subcarrier × I/Q + header)
อัตราส่ง          = 100 packet/วินาที
หน้าต่าง          = 200 packet · stride 50 → ทำนาย 2 ครั้ง/วินาที
```

### ทางเลือก A — ESP32 คำนวณ feature เอง

```
buffer ที่ต้องใช้  200 pkt × 52 subcarrier × float32 = 40.6 KB
ESP32 มี SRAM 520 KB · เหลือ heap หลัง WiFi ~150–250 KB  → พอ

payload  416 float เป็น JSON ≈ 3.8 KB ต่อครั้ง
         × 2 ครั้ง/วินาที = 7.5 KB/s
         → 18.7 GB/เดือน ต่อบ้าน
```

### ทางเลือก B — ส่ง raw ขึ้น cloud ให้ server คำนวณ

```
511 B × 100/วินาที = 49.9 KB/s  → 123.4 GB/เดือน ต่อบ้าน
บีบเป็น binary (int16) แล้ว     →  66.6 GB/เดือน ต่อบ้าน
```

**ตัดทิ้งได้เลย** — 10 บ้านก็ 1.2 TB/เดือน ค่า egress อย่างเดียวก็เกินราคาสินค้า
และเน็ตบ้านคนไทยหลายที่มี FUP

### ทางเลือก A2 — A + ส่งเฉพาะตอนมีการเคลื่อนไหว ⭐

คนอยู่บ้านเงียบ ๆ ส่วนใหญ่ของวัน — ไม่มีเหตุผลที่ต้องส่ง feature ทุก 0.5 วินาทีตลอด 24 ชั่วโมง

ให้ ESP32 คำนวณค่าความแปรปรวนแบบง่าย ๆ ก่อน (std ของ subcarrier ไม่กี่ตัว)
ถ้าต่ำกว่าเกณฑ์ = ไม่มีใครขยับ = **ไม่ต้องส่ง**

```
ถ้าส่งจริง  5% ของเวลา →  0.93 GB/เดือน
ถ้าส่งจริง 10% ของเวลา →  1.87 GB/เดือน
```

ลดลง 10–20 เท่า และประหยัดทั้งค่า cloud, ค่าไฟ ESP32, และโหลดของ ML service

> ⚠️ **ความเสี่ยงที่ต้องระวัง:** ถ้าตั้งเกณฑ์สูงไป การล้มบางแบบอาจถูกกรองทิ้งก่อนถึงโมเดล
> กลายเป็น false negative ที่ไม่มีใครรู้ตัวเลย เพราะไม่มี log ว่ามันเคยเกิด
>
> **ต้องหาเกณฑ์จากข้อมูลจริง** — เอา dataset ที่เก็บไว้มาดูว่าช่วง "ล้ม" มีค่าความแปรปรวน
> ต่ำสุดเท่าไร แล้วตั้งเกณฑ์ให้ต่ำกว่านั้นมาก ๆ ไม่ใช่เดาเอา
> และควร log ทุกครั้งที่กรองทิ้ง เพื่อตรวจย้อนหลังได้

## 3. ข้อเสนอ

**เลือกทางเลือก A2** — ESP32 คำนวณ feature เอง + ส่งเฉพาะตอนมีการเคลื่อนไหว
ยิงเข้า **Express API `/api/v1/predict`** ไม่ใช่ ML service ตรง ๆ

```
ESP32 ─┬─ เก็บ CSI เข้า ring buffer (200 pkt)
       ├─ ทุก 50 pkt: เช็คความแปรปรวนก่อน
       │    ├─ นิ่ง → ทิ้ง ไม่ส่ง
       │    └─ ขยับ → คำนวณ 416 features
       └─ HTTPS POST /api/v1/predict  (x-api-key: DEVICE_API_KEY)
                     device_id = devices.code เช่น "ESP-0001A"
                          │
                          ▼
              Express API ─► ML service ─► บันทึก event ─► alert ─► push ─► escalation
```

**ข้อดีของการยิงเข้า Express API:** ได้ flow แจ้งเตือนทั้งหมดที่สร้างไว้แล้วฟรี ๆ —
cooldown, escalation timer, alert ในแอป, admin dashboard ทำงานครบทันที
ไม่ต้องเขียนอะไรเพิ่มฝั่ง backend เลย

## 4. งานที่ต้องทำถ้าเลือก A2

| # | งาน | ที่ไหน | หมายเหตุ |
|---|---|---|---|
| 1 | หาเกณฑ์ความแปรปรวนจาก dataset จริง | `ml_service/experiments/` | **ทำก่อนเขียน firmware** ตัวเลขนี้กำหนดทุกอย่าง |
| 2 | ring buffer + คำนวณ 8 สถิติ × 52 subcarrier | `_components/` (ใหม่) | ต้องตรงกับ `preprocess_v2.py` **เป๊ะ ๆ** ไม่งั้นโมเดลเจอ input คนละอย่างกับตอนเทรน |
| 3 | HTTPS client + retry/backoff | `_components/` (ใหม่) | เน็ตบ้านหลุดบ่อย ต้องมี buffer ไม่ใช่ทิ้งเลย |
| 4 | อ่าน device code + API key จาก NVS | ต่อยอด `provisioning_component.h` | key ต้องไม่ hardcode ในภาพ firmware |
| 5 | ทดสอบว่าค่าที่ ESP32 คำนวณ ตรงกับ Python | เทียบข้อมูลชุดเดียวกันสองทาง | **สำคัญที่สุด** — ต่างกันนิดเดียวโมเดลก็เพี้ยน |

### ⚠️ ข้อ 5 คือจุดที่พังเงียบที่สุด

`preprocess_v2.py` ใช้ `scipy.stats.skew` และ `kurtosis` ซึ่งมีนิยามเฉพาะ
(kurtosis ของ scipy เป็น *excess* kurtosis คือลบ 3 แล้ว)
ถ้าเขียน C ตามสูตรตำราตรง ๆ จะได้คนละค่า และ **โมเดลจะทำนายเพี้ยนโดยไม่มี error อะไรเลย**

ต้องมีเทสต์ที่เอาข้อมูลชุดเดียวกันเข้าทั้งสองทาง แล้วเทียบ 416 ค่าให้ตรงกัน
ก่อนเอาไปใช้จริง

## 5. ทางเลือกอื่นที่พิจารณาแล้วตัดออก

| ทางเลือก | ทำไมตัด |
|---|---|
| ให้ ESP32 รันโมเดลเอง (edge inference) | RandomForest 300 ต้นใหญ่เกิน · ถ้าจะทำต้อง train โมเดลเล็กใหม่ทั้งหมด · และแก้โมเดลทีต้อง flash ใหม่ทุกเครื่อง |
| ให้ลูกค้าติด Raspberry Pi เป็น gateway | เพิ่มของที่ต้องขาย/ติดตั้ง/ดูแลอีกชิ้น · ต้นทุนต่อบ้านสูงขึ้นมาก |
| ส่ง raw ผ่าน MQTT แทน HTTP | ลด overhead ได้บ้าง แต่ bandwidth ยังอยู่ระดับสิบ GB ไม่แก้ปัญหาหลัก |

## 6. สิ่งที่ยังไม่รู้และต้องวัด

1. **ESP32 คำนวณทันไหม** — 8 สถิติ × 52 subcarrier ทุก 0.5 วินาที พร้อมกับรับ CSI 100 pkt/s
   และรัน WiFi ไปด้วย · `skew`/`kurtosis` ต้องวนข้อมูล 200 ตัวหลายรอบ
   **ต้องวัดบนบอร์ดจริง ไม่ใช่ประมาณ**
2. **heap เหลือจริงเท่าไร** หลังเปิด WiFi + AP + STA (BLE คืนหน่วยความจำไปแล้วหลัง provisioning)
3. **โมเดลทำงานข้ามช่องสัญญาณได้ไหม** — เรื่องที่บันทึกไว้แล้วใน `CLAUDE.md`
   ในโหมด AP+STA ช่องถูกบังคับตามเราเตอร์บ้าน ไม่ใช่ช่อง 6 เหมือนตอนเก็บข้อมูล

> ข้อ 3 อาจทำให้ทุกอย่างในเอกสารนี้เปลี่ยน — ถ้าโมเดลใช้ข้ามช่องไม่ได้
> ต้องกลับไปแก้ที่วิธีเก็บข้อมูลก่อน ไม่ใช่แก้ที่ทางส่งข้อมูล

## 7. ลำดับที่ควรทำ

1. **เก็บ dataset ชุดใหม่ให้เสร็จก่อน** (งานที่ค้างอยู่แล้ว) — ต้องใช้หาเกณฑ์ในข้อ 4.1
   และใช้ตอบข้อ 6.3 เรื่องข้ามช่องสัญญาณ
2. หาเกณฑ์ความแปรปรวนจากข้อมูลจริง
3. วัดว่า ESP32 คำนวณทันไหม (เขียนโค้ดทดสอบสั้น ๆ flash ลงบอร์ด)
4. ค่อยเขียน firmware ตัวจริง

**อย่าเพิ่งเขียน firmware ก่อนทำข้อ 1–3** — ถ้าโมเดลใช้ข้ามช่องไม่ได้ หรือ ESP32
คำนวณไม่ทัน สถาปัตยกรรมจะเปลี่ยนทั้งหมด
