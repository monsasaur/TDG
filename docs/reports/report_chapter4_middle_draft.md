# ผลการดำเนินงาน

> หมายเหตุสำหรับผู้เขียน (ลบออกก่อนรวมเล่ม): ส่วนที่มีเครื่องหมาย ⟪รอเติม⟫ คือผลทดสอบสดกับบอร์ดจริงและการทดสอบย้ายตำแหน่งบอร์ด
> ซึ่งจะเติมหลังทดสอบเสร็จ · ห้ามใส่ค่าคาดการณ์จากสไลด์ลงในรายงาน · ตัวเลขอื่นในบทนี้ตรวจกับโค้ดและผลทดสอบจริง ณ วันที่ 25 พฤศจิกายน 2569
> ภาพที่ระบุไว้ยังเป็นเพียงคำบรรยาย ต้องแคปหน้าจอหรือส่งออกภาพมาใส่

บทนี้นำเสนอผลการพัฒนาระบบตรวจจับการล้มของผู้สูงอายุด้วย WiFi CSI และแอปพลิเคชันแจ้งเตือนผู้ดูแล ตามการออกแบบในบทที่ 3 โดยแบ่งเป็นผลการพัฒนาแต่ละส่วนของระบบ ได้แก่ อุปกรณ์ตรวจจับและการเก็บข้อมูล บริการ Machine Learning, Backend API, ฐานข้อมูล และแอปพลิเคชัน Middle จากนั้นจึงนำเสนอผลการทดสอบระบบ ปัญหาที่พบระหว่างการทดสอบพร้อมแนวทางแก้ไข และผลการประเมินโมเดลตรวจจับการล้ม

## ผลการพัฒนาอุปกรณ์ตรวจจับและการเก็บข้อมูล CSI

ส่วนอุปกรณ์ตรวจจับพัฒนาด้วยบอร์ด ESP32 จำนวน 2 ตัว โดยดัดแปลงจากโครงการ ESP32-CSI-Tool บอร์ดตัวที่ 1 ทำงานในโหมด Access Point สร้างเครือข่าย WiFi ที่ช่องสัญญาณ 6 แบบคงที่ และอ่านค่า CSI จาก packet ที่ได้รับ ส่วนบอร์ดตัวที่ 2 ทำงานในโหมด Station เชื่อมต่อกับบอร์ดตัวที่ 1 และส่ง packet อย่างต่อเนื่องเพื่อให้บอร์ดตัวที่ 1 วัดการเปลี่ยนแปลงของสัญญาณได้ ข้อมูล CSI จากบอร์ดตัวที่ 1 ถูกส่งออกทาง USB Serial ที่ความเร็ว 921600 baud ไปยังคอมพิวเตอร์ที่ใช้เก็บข้อมูล

ในระหว่างการพัฒนาพบว่าอัตราการรับข้อมูล CSI ของชุดข้อมูลแรกอยู่ที่ประมาณ 73 packet ต่อวินาที ต่ำกว่าค่าที่ตั้งไว้ 100 packet ต่อวินาที เนื่องจากข้อผิดพลาดใน firmware หลังแก้ไข firmware อัตราการรับข้อมูลผ่าน USB Serial อยู่ที่ 98–100 packet ต่อวินาทีอย่างสม่ำเสมอ ผู้พัฒนาได้ทดลองส่งข้อมูลผ่าน WiFi แบบ UDP ไปยังคอมพิวเตอร์ด้วย แต่พบว่าอัตราลดลงเป็นช่วงๆ ต่ำสุดเหลือประมาณ 24 packet ต่อวินาที เนื่องจากระบบปฏิบัติการของคอมพิวเตอร์สแกนหาเครือข่าย WiFi เป็นระยะ จึงเลือกใช้ USB Serial เป็นช่องทางหลักในการเก็บข้อมูล โดยวัดอัตราจากเวลาที่บันทึกในตัว packet ของ ESP32 ไม่ใช่เวลาของคอมพิวเตอร์

ตารางที่ 4.1 ผลการวัดอัตราการรับข้อมูล CSI

| รูปแบบการรับข้อมูล | อัตราที่วัดได้ (packet/วินาที) | หมายเหตุ |
|---|---|---|
| USB Serial — firmware เดิม (ชุดข้อมูลแรก) | ประมาณ 73 | ข้อผิดพลาดใน firmware |
| USB Serial — firmware ที่แก้ไขแล้ว | 98–100 | คงที่ตลอดการเก็บข้อมูล ใช้เป็นช่องทางหลัก |
| WiFi แบบ UDP ไปยังคอมพิวเตอร์ | ต่ำสุดประมาณ 24 | ขาดเป็นช่วงจากการสแกน WiFi ของระบบปฏิบัติการ |

สำหรับการเก็บชุดข้อมูล ผู้พัฒนาได้สร้างเครื่องมือเก็บข้อมูลแบบหน้าเว็บ (`collect_web.py`) ที่ใช้งานบนเครื่องคอมพิวเตอร์ ผู้เก็บข้อมูลเลือกผู้แสดงและท่าทาง แล้วกดปุ่มเพื่อบันทึกแต่ละครั้ง เครื่องมือแสดงอัตราการรับข้อมูลแบบเวลาจริง มีแผงทดสอบคุณภาพลิงก์ก่อนเริ่มเก็บ และบันทึกข้อมูลประจำรอบ (manifest) ระบุผู้แสดงของแต่ละไฟล์ เพื่อให้แบ่งข้อมูลทดสอบตามผู้แสดงได้ในขั้นตอนประเมินโมเดล ชุดข้อมูลรอบที่สองเก็บจากผู้แสดง 5 คน รวม 801 ไฟล์ โดยสลับท่าล้มและท่าที่ไม่ใช่การล้มภายในรอบเดียวกัน

ภาพที่ 4.1 อุปกรณ์ ESP32 ทั้งสองตัวในพื้นที่ทดสอบ

ภาพที่ 4.2 หน้าเว็บเครื่องมือเก็บข้อมูล CSI

นอกจากโหมดเก็บข้อมูล firmware ของบอร์ดตัวที่ 1 ยังมีโหมดสำหรับการใช้งานจริง ซึ่งเปิดให้แอปพลิเคชันตั้งค่า WiFi ของบ้านผ่าน Bluetooth Low Energy (BLE) ด้วยระบบ provisioning ของ ESP-IDF แบบ Security 1 ที่ยืนยันด้วยรหัสจับคู่ (Proof of Possession) การพัฒนาส่วนนี้ต้องขยายพื้นที่โปรแกรมเป็น 2 MB บนหน่วยความจำ flash ขนาด 4 MB และเปิดใช้ NimBLE ผลการทดสอบเมื่อวันที่ 13 ตุลาคม 2569 พบว่า firmware คอมไพล์และติดตั้งลงบอร์ดได้ และสมาร์ตโฟนมองเห็นอุปกรณ์ผ่าน BLE แต่ยังไม่ได้ทดสอบการส่งข้อมูล WiFi ผ่าน BLE จนครบขั้นตอน

## ผลการพัฒนาบริการ Machine Learning

บริการ Machine Learning พัฒนาด้วย Python และ FastAPI มี endpoint หลัก 2 เส้น ได้แก่ `POST /predict` สำหรับรับ feature แล้วคืนผลการตรวจจับ และ `GET /health` สำหรับตรวจสอบสถานะบริการ ผลลัพธ์ที่ส่งกลับประกอบด้วย prediction, confidence และ risk_score

บริการรองรับโมเดล 2 รุ่น เลือกด้วยตัวแปรสภาพแวดล้อม `FALL_MODEL` ได้แก่ `rf_v1` ซึ่งเป็นค่าเริ่มต้น รับ feature 416 ค่าและใช้ threshold 0.55 และ `rf_v2_event` ซึ่งใช้ feature แบบเหตุการณ์ 39 ค่า (รวมความเร็วการเคลื่อนไหวแบบ Doppler และช่วง 1.5 วินาทีหลังเหตุการณ์) ใช้ threshold 0.5 และต้องยืนยัน 2 กรอบติดกันก่อนแจ้ง สำหรับการตรวจจับแบบต่อเนื่อง นอกจากนี้ยังพัฒนาเครื่องมือตรวจจับสด (`fall_monitor.py`) ที่อ่านข้อมูลจาก ESP32 และแสดงผลการตรวจจับแบบเวลาจริงสำหรับการทดสอบในพื้นที่

ภาพที่ 4.3 หน้าเอกสาร API ของบริการ Machine Learning

## ผลการพัฒนา Backend API

Backend API พัฒนาด้วย Node.js และ Express ทำหน้าที่เป็นศูนย์กลางของระบบ รับข้อมูลจากอุปกรณ์ เรียกใช้บริการ Machine Learning บันทึกเหตุการณ์ ส่งการแจ้งเตือน และจัดการขั้นตอนการยกระดับการแจ้งเตือน endpoint หลักของระบบแสดงในตารางที่ 4.2

ตารางที่ 4.2 endpoint หลักของ Backend API

| Method | Endpoint | หน้าที่ | การยืนยันตัวตน |
|---|---|---|---|
| POST | /api/v1/predict | รับ feature จากอุปกรณ์ เรียก ML Service และเริ่มการแจ้งเตือนเมื่อตรวจพบการล้ม | API key ของอุปกรณ์ |
| POST | /api/v1/alert/ack/:event_id | ผู้ดูแลยืนยันรับทราบ และยกเลิกการโทรแจ้งเตือน | API key ของแอป + token ของบัญชีผู้ใช้ที่เป็นสมาชิกบ้าน |
| POST | /api/v1/push/register | ลงทะเบียน push token และผูกสมาร์ตโฟนกับบัญชีผู้ใช้ | API key ของแอป (+ token ของบัญชีเมื่อเข้าสู่ระบบ) |
| GET | /api/v1/events, /events/falls | รายการเหตุการณ์ของทุกบ้าน (ใช้ตรวจสอบระบบ) | API key สำหรับสาธิต |
| POST | /api/v1/demo/fire | จำลองเหตุการณ์การล้มสำหรับสาธิต โดยข้ามขั้นตอน ML | API key สำหรับสาธิต |
| POST | /api/v1/alert/test | ทดสอบการโทรผ่าน Twilio | API key สำหรับสาธิต |
| POST | /api/v1/admin/login | เข้าสู่ระบบของผู้ดูแลระบบ | ชื่อผู้ใช้และรหัสผ่าน |
| GET | /api/v1/admin/summary, events, events/:id, devices | ข้อมูลสรุป เหตุการณ์ และสถานะอุปกรณ์ทุกบ้าน | Bearer token ของผู้ดูแลระบบ |
| GET | /admin | หน้าเว็บผู้ดูแลระบบ (ไฟล์ static) | ต้องเข้าสู่ระบบผู้ดูแลระบบก่อนเห็นข้อมูล |
| GET | /health | ตรวจสอบสถานะบริการ | ไม่ต้องยืนยัน |

API key แยกตามขอบเขตการใช้งาน ได้แก่ คีย์ของอุปกรณ์ คีย์ของแอปพลิเคชัน และคีย์สำหรับการสาธิต เพื่อไม่ให้คีย์ที่ฝังอยู่ในแอปพลิเคชันสามารถสั่งให้ระบบโทรออก หรืออ่านข้อมูลของทุกบ้านได้ เนื่องจากคีย์ของแอปพลิเคชันถูกแกะออกจากไฟล์ติดตั้งได้ การกดรับทราบจึงต้องแนบ token ของบัญชีผู้ใช้ด้วย และ Backend API จะตรวจกับ Supabase Auth ว่าผู้กดเป็นสมาชิกของบ้านที่อุปกรณ์ติดตั้งอยู่ ชื่อผู้กดรับทราบที่บันทึกมาจากบัญชีที่ตรวจแล้ว ไม่ใช่ชื่อที่แอปพลิเคชันส่งมา หากไม่มีการตรวจนี้ ผู้ที่ได้คีย์ไปจะยกเลิกการโทรฉุกเฉินของบ้านอื่นได้ ในทำนองเดียวกัน Push Notification ของแต่ละเหตุการณ์จะส่งเฉพาะสมาร์ตโฟนที่เข้าสู่ระบบเป็นสมาชิกของบ้านนั้น ส่วน endpoint ของผู้ดูแลระบบใช้การยืนยันตัวตนด้วย Bearer token แยกจาก API key เอกสาร API ทั้งหมดสร้างจาก OpenAPI specification ไฟล์เดียว และเปิดให้ทดลองเรียกได้ผ่านหน้า Swagger โดยชุดทดสอบอัตโนมัติจะตรวจว่าทุก route ที่มีจริงถูกบันทึกในเอกสาร และเอกสารที่ส่งออกตรงกับ specification

ภาพที่ 4.4 หน้า Swagger สำหรับทดลองเรียก Backend API

สำหรับทีมดูแลระบบ ผู้พัฒนาได้สร้างหน้าเว็บผู้ดูแลระบบที่ Express ให้บริการที่ `/admin` บน origin เดียวกับ API จึงไม่ต้องตั้งค่า CORS หน้าเว็บประกอบด้วย 4 ส่วน ได้แก่ ภาพรวม (จำนวนอุปกรณ์ที่ออนไลน์ จำนวนการล้มวันนี้และ 7 วันล่าสุด และอัตราที่ต้องโทรฉุกเฉิน) รายการเหตุการณ์ของทุกบ้านที่กรองตามสถานะ อุปกรณ์ และช่วงวันที่ได้ พร้อมไทม์ไลน์ของแต่ละเหตุการณ์ รายการอุปกรณ์และสถานะ และทะเบียนรุ่นของโมเดล การเข้าสู่ระบบใช้ชื่อผู้ใช้และรหัสผ่านของผู้ดูแลระบบซึ่งแยกจากบัญชีของแอปพลิเคชัน และ token ถูกเก็บเฉพาะในแท็บของเบราว์เซอร์ หน้าเว็บนี้ทดสอบกับฐานข้อมูลจริงแล้วเมื่อวันที่ 25 พฤศจิกายน 2569

ภาพที่ 4.5 หน้าเว็บผู้ดูแลระบบ: ภาพรวม และรายการเหตุการณ์พร้อมไทม์ไลน์

กลไกการยกระดับการแจ้งเตือนทำงานดังนี้ เมื่อตรวจพบการล้ม ระบบบันทึกเหตุการณ์ ส่ง Push Notification ไปยังแอปพลิเคชัน และเริ่มจับเวลารอการยืนยัน 60 วินาที หากผู้ดูแลกดรับทราบภายในเวลาดังกล่าว ระบบจะยกเลิกการโทร หากหมดเวลา ระบบจะโทรแจ้งเตือนผ่าน Twilio และบันทึกสถานะการยกระดับ อุปกรณ์เดียวกันจะไม่ถูกแจ้งเตือนซ้ำภายใน 300 วินาที เพื่อป้องกันการแจ้งเตือนถี่เกินไป ตัวจับเวลาถูกเก็บในหน่วยความจำ แต่เมื่อบริการเริ่มทำงานใหม่ ระบบจะอ่านเหตุการณ์ที่ยังรอการยืนยันจากฐานข้อมูลมาตั้งเวลาใหม่ตามเวลาที่เหลือจริง และมีตัวตรวจซ้ำทุก 60 วินาที เหตุการณ์ที่เลยกำหนดเกิน 1 ชั่วโมงจะไม่โทรแต่ปิดสถานะไว้ เพื่อไม่ให้โทรแจ้งเหตุการณ์ที่เก่าเกินไป

ระบบยังมีการโทรแจ้งเตือนด้วยข้อความที่สร้างโดย AI (Hybrid AI escalation ระยะที่ 2a) โดยใช้แบบจำลองภาษา Typhoon ซึ่งเน้นภาษาไทย ร่างข้อความที่ระบุชื่อห้องและชื่อบ้านของเหตุการณ์ การตัดสินใจว่าจะโทรหรือไม่ยังคงเป็นแบบกฎทั้งหมด AI มีหน้าที่เพียงร่างข้อความ หาก AI ไม่ตอบภายใน 3 วินาที ตอบไม่สำเร็จ หรือข้อความไม่ผ่านการตรวจสอบ เช่น มีอักษรโรมันหรือวงเล็บที่แสดงว่าโมเดลเติมข้อมูลไม่ครบ ระบบจะใช้ข้อความมาตรฐานแทนทันที ความสามารถนี้ปิดไว้เป็นค่าเริ่มต้นและเปิดได้ด้วยการตั้งค่าเท่านั้น

## ผลการพัฒนาฐานข้อมูล

ฐานข้อมูลของระบบใช้ Supabase (PostgreSQL) แบ่งตารางเป็น 3 กลุ่ม ได้แก่ กลุ่มตารางของ CSI pipeline ที่ Backend API เขียน กลุ่มตารางของแอปพลิเคชัน และกลุ่มตารางของระบบบัญชีผู้ใช้ ดังตารางที่ 4.3 ตารางเหตุการณ์การล้มเชื่อมกับตารางอุปกรณ์ผ่านรหัสอุปกรณ์ที่พิมพ์บนตัวเครื่อง และทุกครั้งที่ตรวจพบการล้ม Backend API จะสร้างแถวการแจ้งเตือนของบ้านที่อุปกรณ์นั้นติดตั้งอยู่ให้แอปพลิเคชันแสดงผล

ตารางที่ 4.3 ตารางในฐานข้อมูลของระบบ

| กลุ่ม | ตาราง | หน้าที่ |
|---|---|---|
| CSI pipeline | fall_events | เหตุการณ์ที่ตรวจพบ ค่าความมั่นใจ สถานะการรับทราบ และการยกระดับ |
| CSI pipeline | push_tokens | push token ของอุปกรณ์ผู้ดูแล |
| CSI pipeline | ml_models | ทะเบียนรุ่นของโมเดล (เก็บเฉพาะข้อมูลประกอบ ใช้ในหน้าผู้ดูแลระบบ) |
| แอปพลิเคชัน | houses | บ้านหรือพื้นที่ดูแล |
| แอปพลิเคชัน | devices | อุปกรณ์ตรวจจับ ผูกกับบ้าน และสถานะการเชื่อมต่อ |
| แอปพลิเคชัน | alerts | การแจ้งเตือนที่แสดงในแอป ผูกกับเหตุการณ์ใน fall_events |
| แอปพลิเคชัน | emergency_contacts, house_contacts | ผู้ติดต่อฉุกเฉินและการผูกกับบ้าน |
| บัญชีผู้ใช้ | house_members | สมาชิกของแต่ละบ้านและบทบาท (เจ้าของบ้าน / ผู้ดูแล) |
| บัญชีผู้ใช้ | house_invites | รหัสเชิญเข้าบ้าน ใช้ได้ครั้งเดียวและมีวันหมดอายุ |
| บัญชีผู้ใช้ | audit_logs | ประวัติการเปลี่ยนแปลง: ผู้กระทำ บ้านที่เกี่ยวข้อง และค่าก่อน/หลังการแก้ไข |

สิทธิ์การเข้าถึงข้อมูลบังคับที่ฐานข้อมูลด้วย Row Level Security ผู้ใช้เห็นเฉพาะข้อมูลของบ้านที่ตนเป็นสมาชิก เจ้าของบ้านแก้ไขบ้าน อุปกรณ์ และผู้ติดต่อฉุกเฉินได้ ส่วนผู้ดูแลดูข้อมูลและกดรับทราบการแจ้งเตือนได้แต่แก้ไขไม่ได้ ตารางฝั่ง Backend เข้าถึงได้เฉพาะ Backend API ที่ใช้คีย์ระดับบริการ การสร้างบ้านและการเข้าร่วมบ้านทำผ่านฟังก์ชันในฐานข้อมูล ซึ่งตรวจเงื่อนไข เช่น เป็นสมาชิกได้สูงสุด 5 บ้านต่อคน และบ้านหนึ่งมีสมาชิกได้สูงสุด 6 คน ชื่อและเบอร์โทรศัพท์ของสมาชิกซึ่งเก็บในระบบยืนยันตัวตนอ่านได้ผ่านฟังก์ชันที่คืนข้อมูลเฉพาะคนในบ้านเดียวกัน

ฐานข้อมูลบันทึกประวัติการเปลี่ยนแปลง (audit log) เองด้วย trigger ทุกครั้งที่มีการเพิ่ม แก้ไข หรือลบ บ้าน อุปกรณ์ การแจ้งเตือน ผู้ติดต่อฉุกเฉิน สมาชิก และรหัสเชิญ แต่ละรายการระบุผู้กระทำ บ้านที่เกี่ยวข้อง และค่าก่อนและหลังเฉพาะคอลัมน์ที่เปลี่ยน การบันทึกเกิดที่ฐานข้อมูลจึงไม่สามารถข้ามได้จากฝั่งแอปพลิเคชัน และไม่มีผู้ใช้คนใดแก้ไขหรือลบประวัติได้ ผู้ใช้อ่านได้เฉพาะสิ่งที่ตนทำและประวัติของบ้านที่ตนเป็นเจ้าของ

ระบบบัญชีผู้ใช้ทดสอบบนฐานข้อมูลทดสอบก่อน แล้วเปิดใช้บนฐานข้อมูลจริงเมื่อวันที่ 23 พฤศจิกายน 2569 การทดสอบครบเส้นทางบนฐานข้อมูลจริงเมื่อวันที่ 24 พฤศจิกายน 2569 พบว่าตารางบางตารางบนฐานข้อมูลจริงถูกสร้างไว้ก่อนไฟล์ schema รุ่นปัจจุบัน คำสั่งสร้างตารางแบบ "ถ้ายังไม่มี" จึงข้ามไปและโครงสร้างไม่ตรงกัน 3 จุด (รายละเอียดในตารางที่ 4.7) ซึ่งได้แก้ไขแล้ว และเพิ่มการตรวจโครงสร้างดังกล่าวในสคริปต์ตรวจความพร้อมก่อนทดสอบ

## ผลการพัฒนาแอปพลิเคชัน Middle

แอปพลิเคชัน Middle พัฒนาด้วย React Native และ Expo มีทั้งหมด 33 หน้าจอ แบ่งตามกลุ่มการใช้งานดังตารางที่ 4.4

ตารางที่ 4.4 กลุ่มหน้าจอของแอปพลิเคชัน Middle

| กลุ่ม | หน้าจอ | ความสามารถ |
|---|---|---|
| บัญชีผู้ใช้และการตั้งค่า | Splash, Welcome (เข้าสู่ระบบ), Login, Register, Get started, Settings, Notification settings, Activity log | เข้าสู่ระบบด้วยเบอร์โทรศัพท์และรหัสผ่านในหน้าแรก สมัครใช้งาน บัญชีที่ยังไม่มีบ้านถูกพาไปหน้าเริ่มต้นใช้งานเพื่อสร้างบ้านหรือเข้าร่วมด้วย QR / รหัสเชิญ จำการเข้าสู่ระบบไว้ในเครื่อง ตั้งค่าการแจ้งเตือน ดูประวัติการเปลี่ยนแปลง |
| การแจ้งเตือน | Home, Clear alerts | รายการแจ้งเตือนแยกตามบ้าน นับถอยหลังก่อนโทรตามเวลาจริง กดรับทราบ ดูลำดับเหตุการณ์ ลบรายการที่ดูแล้ว |
| บ้านและสมาชิก | Houses, Add house, Manage home, Members, Member detail, Invite (เลือกบ้าน / เลือกวิธี / รหัส / QR), Enter code, Scan QR | สร้างบ้าน ดูสมาชิกและบทบาท เชิญสมาชิกด้วยรหัส 6 ตัวหรือ QR Code เข้าร่วมบ้านด้วยการกรอกรหัสหรือสแกน ผู้ดูแลออกจากบ้านเอง เจ้าของบ้านนำผู้ดูแลออก |
| อุปกรณ์ | Devices, Device details, Scan devices, Pairing code, Connect device, Add network, WiFi password, Select house, Device setup | ค้นหาอุปกรณ์ผ่าน BLE กรอกหรือสแกนรหัสจับคู่ ส่งข้อมูล WiFi ให้อุปกรณ์ และบันทึกอุปกรณ์เข้าบ้าน |
| ผู้ติดต่อฉุกเฉิน | Emergency contacts, Add contact, Edit contact | จัดการรายชื่อผู้ติดต่อฉุกเฉินของแต่ละบ้าน |

หน้าหลักของแอปพลิเคชันดึงรายการแจ้งเตือนจากฐานข้อมูลทุก 10 วินาที ส่วนการแจ้งเตือนแบบทันทีส่งผ่าน Push Notification ซึ่งทดสอบบนสมาร์ตโฟน Android ผ่าน Firebase Cloud Messaging (FCM V1) เมื่อผู้ดูแลกดรับทราบ แอปพลิเคชันจะแสดงผลทันทีแล้วจึงส่งคำขอไปยัง Backend API หากส่งไม่สำเร็จจะย้อนสถานะกลับและแจ้งผู้ใช้ เพื่อไม่ให้หน้าจอแสดงว่ารับทราบแล้วในขณะที่ระบบยังจะโทรแจ้งเตือน และหากระบบโทรออกไปแล้วก่อนที่ผู้ดูแลจะกด แอปพลิเคชันจะแสดงสถานะว่ากำลังโทรแจ้งเตือนแทน ชื่อผู้กดรับทราบที่แสดงให้สมาชิกคนอื่นเห็นมาจากชื่อของบัญชีผู้ใช้

การนับถอยหลังบนการ์ดแจ้งเตือนคำนวณจากเวลาที่เกิดเหตุการณ์จริง ไม่ได้เริ่มนับใหม่ทุกครั้งที่เปิดแอปพลิเคชัน ผู้ดูแลที่เปิดแอปพลิเคชันหลังเกิดเหตุไปแล้วจึงเห็นเวลาที่เหลือจริงก่อนระบบจะโทรแจ้งเตือน ส่วนการลบการแจ้งเตือนเป็นการซ่อนจากรายการของบัญชีนั้นบนสมาร์ตโฟนเครื่องนั้น สมาชิกคนอื่นยังเห็นและประวัติเหตุการณ์ยังอยู่ครบ โดยการแจ้งเตือนที่ยังรอการรับทราบจะไม่ถูกซ่อน เพื่อไม่ให้เหตุฉุกเฉินที่ยังนับถอยหลังหายไปจากหน้าจอ

### การทดสอบอัตโนมัติ

ผู้พัฒนาได้เขียนชุดทดสอบอัตโนมัติสำหรับแต่ละส่วนของระบบ และตั้งให้ชุดทดสอบของ Backend API บริการ Machine Learning และการตรวจชนิดข้อมูลกับรูปแบบโค้ดของแอปพลิเคชัน ทำงานอัตโนมัติบน GitHub Actions ทุกครั้งที่ส่งโค้ดขึ้น branch พัฒนาหรือขอรวมโค้ดเข้า branch หลัก ผลการทดสอบแสดงในตารางที่ 4.5

## ผลการประเมินโมเดลตรวจจับการล้ม

### ชุดข้อมูลแรกและปัญหาที่พบ

ชุดข้อมูลแรก (804 ไฟล์ ผู้แสดง 5 คน) ได้ความแม่นยำ 95.6% ด้วย Random Forest ที่แบ่งชุดทดสอบตามไฟล์บันทึก แต่การตรวจสอบพบว่าชุดข้อมูลนี้เก็บท่าล้มทั้งหมดก่อนท่าที่ไม่ใช่การล้ม สภาพของห้องในแต่ละช่วงเวลาจึงสัมพันธ์กับประเภทของข้อมูล โมเดลแยกข้อมูลได้จากช่วงเวลาที่เก็บมากกว่าจากลักษณะการล้ม ตัวเลข 95.6% จึงใช้เป็นผลในสภาพแวดล้อมอุดมคติเท่านั้น ส่วนตัวเลข 99.7% ของโมเดล LSTM ที่รายงานในช่วงแรกวัดด้วยการแบ่งข้อมูลที่ช่วงเดียวกันอยู่ทั้งในชุดฝึกและชุดทดสอบ จึงไม่นำมาใช้

### ชุดข้อมูลรอบที่สองแบบ unseen

ชุดข้อมูลรอบที่สอง (801 ไฟล์ ผู้แสดง 5 คน สลับท่าภายในรอบ) ประเมินแบบ unseen คือฝึกด้วยผู้แสดง 4 คนแล้วทดสอบกับผู้แสดงคนที่ 5 ที่โมเดลไม่เคยเห็น วนจนครบทุกคน วัดบน 752 ครั้งที่มีข้อมูลหลังเหตุการณ์อย่างน้อย 1.5 วินาที และใช้ balanced accuracy ผลการเพิ่ม feature ทีละขั้นแสดงในตารางที่ 4.8

ตารางที่ 4.8 ความแม่นยำแบบ unseen เมื่อเพิ่ม feature ทีละขั้น (แจ้งเมื่อล้มหรือนอนอยู่บนพื้น)

| ขั้น | การเปลี่ยนแปลง | balanced accuracy |
|---|---|---|
| ตัวเก่า | feature แบบเหตุการณ์ แจ้งเฉพาะการล้ม | 72.4% |
| 1 | แจ้งทั้งการล้มและการนอนอยู่บนพื้น | 74.5% |
| 2 | เพิ่มความเร็วการเคลื่อนไหว (Doppler) | 77.8% |
| 3 | เพิ่มข้อมูล 1.5 วินาทีหลังเหตุการณ์ | 86.5% |
| 4 | เฉลี่ยคะแนนหลายกรอบรอบเหตุการณ์ (ตัวที่ใช้) | 87.1% |

ค่า AUC เพิ่มจาก 0.78 เป็น 0.95 ผลรายผู้แสดงดีขึ้นทุกคน จากช่วง 71–77% เป็น 84–90% อัตราการแจ้งผิดลดลงราวครึ่งหนึ่ง เช่น ยืนนิ่งจาก 54% เหลือ 19% เดินจาก 33% เหลือ 16% และสะดุดแต่ไม่ล้มจาก 40% เหลือ 21% ส่วนการล้มไปด้านข้างซึ่งตรวจจับยากที่สุดจับได้เพิ่มจาก 72% เป็น 82% หากแจ้งเฉพาะการล้มโดยไม่นับการนอนบนพื้น ความแม่นยำแบบ unseen อยู่ที่ 81.1%

ผู้พัฒนาตรวจสอบว่าผลไม่ได้เกิดจากความบังเอิญ 4 วิธี ได้แก่ ช่วงความเชื่อมั่น 95% ด้วย bootstrap 2,000 รอบอยู่ที่ 84.6–89.4% · ฝึกด้วยผู้แสดง 2 คนแรกแล้วทดสอบกับอีก 3 คนที่ไม่เคยใช้ได้ 89.2% · สลับ label แบบสุ่ม 10 รอบได้สูงสุด 52.4% ซึ่งเท่ากับการเดา · และโมเดลที่ใช้ดีกว่าตัวเก่า 12.6 จุด โดยช่วงความเชื่อมั่นอยู่ที่ +9.5 ถึง +15.9 จุดซึ่งไม่คร่อมศูนย์

ภาพที่ 4.14 ความแม่นยำแบบ unseen รายผู้แสดง เทียบตัวเก่ากับตัวที่ใช้

### การตรวจจับแบบต่อเนื่อง

ในการใช้งานจริง ระบบไม่ทราบจังหวะของเหตุการณ์ล่วงหน้า จึงประเมินเพิ่มด้วยการเลื่อนกรอบทุก 0.25 วินาทีบนไฟล์ที่บันทึกไว้ โมเดลที่ใช้ในระบบจับการล้มได้ 64.2% (รุ่นก่อน 43%) โดยไม่แจ้งผิดในไฟล์กิจวัตรจริงรวม 8.5 นาที ทั้งนี้ข้อมูลกิจวัตรยังสั้น การแจ้งผิด 1 ครั้งในช่วงนี้จะเท่ากับราว 7 ครั้งต่อชั่วโมง ผลนี้จึงต้องยืนยันด้วยการทดสอบสด
